Every time you type a command on your Pi, something quietly remarkable happens underneath: a process is born, runs your program, and dies — and the shell is right there to catch its last breath. In this chapter we go deeper than "type a command and watch it run." You'll see how processes are actually created, why "zombie" and "orphan" mean very different things, how a single keystroke like Ctrl-C turns into a signal, and the real difference between &, nohup, and disown. Your Pi 5 runs full Debian with systemd and bash, so every word here applies to the little board on your desk.

fork + exec: the two-step behind everything

Here's a fact that surprises most people: on Linux, a brand-new process is never created from nothing. There is no "make me a fresh program" button. Instead, Unix has exactly two moves, and your shell uses them millions of times a day.

  • fork() — clone the current process. You now have two nearly identical processes: the parent and a child copy. The child even keeps the same open files.
  • exec() — replace the program running inside a process with a different one, keeping the same PID and the same open files. The memory gets overwritten with the new program, but the wrapper stays.
In plain words: Think of fork as a photocopier that duplicates a worker, and exec as that copy taking off its uniform and putting on a completely different one — same employee badge number, brand-new job. The shell forks a copy of itself, and the copy then "becomes" ls by calling exec.

When you run ls in your Pi's terminal, this is the dance:

shell process
   | fork()              clone: child is a near-identical copy (same open files!)
   v
child (still the shell's code)
   | set up redirections  rearrange files 0/1/2 here, because they survive exec
   | exec("/bin/ls")      overwrite memory with ls; SAME pid, SAME open files
   v
child is now ls, already wired up to your terminal
   | exit(0)
   v
shell wait()s, collects the exit code -> $?

The key insight: shell redirection (the >, <, and | you've already met) works because fork preserves the file table and exec does not reset it. The shell forks, the child quietly points its output at your file, then execs your command — which inherits the redirected output and never even knows it was redirected. One model, two parts, endless consequences.

Tip: You can watch this happen for real on your Pi. Run strace -f -e trace=clone,execve,wait4 bash -c 'ls > /tmp/x' and you'll see the clone (fork), the execve, and the wait4 with your own eyes. Install it first with sudo apt install strace.

The process tree, PID 1, orphans & zombies

Every process on your Pi has a parent, recorded as its PPID (parent process ID). Follow those parents upward and you always arrive at the same place: PID 1, which on a modern Pi is systemd. The kernel starts PID 1 at boot, and the whole tree grows from there.

pstree -p                          # the whole tree, with PIDs
ps -eo pid,ppid,stat,cmd           # STAT column: Z=zombie  D=uninterruptible  S=sleep  R=running  +=foreground

Two states confuse almost everyone, so let's pin them down precisely.

Zombie (the misunderstood one)

A zombie — shown as Z or "defunct" — is a process that has already exited but whose parent hasn't yet called wait() to collect its exit status. A zombie holds no memory and runs no code. It is just a PID and an exit code lingering in the process table, waiting to be read.

Careful: You cannot kill a zombie — it is already dead. kill -9 does nothing to it, because there is nothing left to kill. A pile of zombies means the parent is buggy and isn't reaping its children. The fix is always to fix or kill the parent, which lets PID 1 clean up the leftovers.

Orphan (the harmless one)

An orphan is a process whose parent died first. The kernel notices and re-parents it to PID 1, which dutifully reaps it when it finishes. Orphans are completely normal and harmless.

The key insight: a zombie is a pathology (a parent that forgot its job); an orphan is routine (the system tidying up automatically). They sound similar but they are opposites in spirit.

Note: This matters more than it looks, especially when you start running containers on your Pi later. Inside a container, your app is often PID 1. If it doesn't reap children and forward signals the way a real init does, you get zombie buildup and docker stop hangs (because nothing handles the shutdown signal). That's exactly why docker run --init and tools like tini exist. PID 1 is special — and now you know why.

Signals — the precise, commonly-botched distinctions

A signal is a short, asynchronous notification the kernel delivers to a process — a tap on the shoulder saying "something happened, deal with it." A handful matter day to day, and the differences between them trip people up constantly.

Signal#Catchable?Meaning
SIGTERM15yes"Please shut down." The polite default of kill. The app gets to clean up first.
SIGINT2yesCtrl-C — interrupt the program running in the foreground.
SIGHUP1yesOriginally "the terminal hung up"; now widely repurposed as "reload your config" for daemons (e.g. nginx -s reload).
SIGKILL9NOUncatchable, unblockable, unignorable. The kernel destroys the process outright. No cleanup runs.
SIGSTOP / SIGCONT19 / 18STOP: noPause / resume. The basis of Ctrl-Z plus fg and bg.
Myth vs reality: The myth is "kill -9 is how you kill a process." The reality is that kill -9 (SIGKILL) is the brutal last resort. Because it can't be caught, the process gets no chance to flush buffers, finish writes, release locks, or reap its own children — so you can corrupt data, strand locks, and leave zombies behind. Always send SIGTERM first (plain kill PID, no flag) and escalate to -9 only if the process ignores you. And SIGKILL isn't even omnipotent: a process stuck in uninterruptible sleep (state D, blocked inside a syscall — usually waiting on disk or a slow USB drive on your Pi) won't die even to SIGKILL until that I/O completes.
kill -l                    # list every signal name and number
kill 1234                  # polite: sends SIGTERM
kill -TERM 1234            # exactly the same, but explicit
kill -HUP $(pgrep nginx)   # tell nginx to reload its config
kill -9 1234              # SIGKILL — only after TERM has been ignored

&, nohup, disown — three different things people conflate

You'll often want a long job to keep running on your Pi while you do something else — or even after you close the terminal or log out over SSH. Three tools get mixed up here, and they work by genuinely different mechanisms.

You runMechanismSurvives terminal close?Redirects output?
cmd &Background job, still a child of the shellOften no (gets SIGHUP)No
nohup cmd &Sets the process to ignore SIGHUP; sends output to nohup.outYesYes
cmd & then disownRemoves the job from the shell's job table, so it won't be sent SIGHUP on exitYesNo

The key insight: they solve overlapping problems by different mechanisms. nohup changes the process's signal disposition before launch. disown changes the shell's bookkeeping after launch. Plain & does neither robustly — it just runs the job in the background and crosses its fingers.

Tip: For real detachment on a Pi you SSH into, the modern answers are nicer than any of these. Use a tmux or screen session for interactive work you want to reconnect to later, or a proper systemd service (or systemd-run --user --scope) for anything that should outlive your login and restart on boot. You'll meet systemd services properly a little later.

Job control & sessions (where Ctrl-C and Ctrl-Z come from)

Here's where those familiar keystrokes finally make sense. A terminal session has exactly one foreground process group and any number of background groups. When you build a pipeline like a | b | c, all three commands join a single process group — which is why one Ctrl-C stops the whole pipeline at once, not just the last stage.

The terminal translates your keystrokes into signals sent to the foreground group:

  • Ctrl-C sends SIGINT — interrupt.
  • Ctrl-\ sends SIGQUIT — interrupt plus a core dump.
  • Ctrl-Z sends SIGTSTP — suspend. Then bg resumes it in the background, fg pulls it back to the foreground, and jobs lists what you've got.
sleep 1000        # now press Ctrl-Z to suspend it
jobs              # [1]+  Stopped    sleep 1000
bg %1             # resume it in the background
fg %1             # pull it back to the foreground
In plain words: "Foreground" just means the program currently holding the keyboard — the one your typing and Ctrl-C go to. "Background" jobs are still running but no longer connected to your keystrokes. Job control is simply your shell letting you shuffle programs between those two states.

Try it on your Pi

These hands-on labs drive every idea above. They're safe to run on your everyday Pi, but if you'd rather experiment freely, do them on a spare microSD card you can re-flash if anything goes sideways.

  1. Signals & job-control survey. Start a sleep 500, suspend it with Ctrl-Z, then juggle it with jobs, bg %1, and fg %1. Open a second terminal, find its PID with pgrep sleep, and send it kill -STOP then kill -CONT then kill -TERM. Prove to yourself that SIGTERM ends it cleanly.
  2. SIGKILL can't be trapped. Write a tiny bash script with trap 'echo caught' SIGTERM and an infinite loop. Send it SIGTERM and watch it print "caught" — then send kill -9 and watch it vanish without a word. You've just felt the difference between catchable and uncatchable.
  3. Zombie & orphan lab. Make a zombie (a parent that forks a child, the child exits, but the parent never waits) and an orphan (a parent that exits before its child). Watch both with ps -eo pid,ppid,stat,cmd and pstree -p. Confirm you cannot kill -9 the zombie, and that the orphan's PPID has become 1.
  4. Graceful shutdown handler. Write a worker script that traps SIGTERM and SIGINT, finishes its in-flight task, deletes its temp files, and then exits — instead of dying instantly. In bash: trap 'cleanup' SIGTERM SIGINT EXIT. This is exactly the pattern a well-behaved systemd service or container app must follow to shut down cleanly.

Key terms

  • fork() - The system call that clones the calling process into a near-identical child, which keeps the same open files. Every new process starts as a fork of an existing one.
  • exec() - The system call that replaces the program running inside a process with a different one, keeping the same PID and open files. Forks then exec to launch a new command.
  • PID / PPID - A process's own ID and its parent's ID. Following PPIDs upward always leads to PID 1.
  • PID 1 - The first process the kernel starts (systemd on a modern Pi); the root of the process tree and the adopter of all orphans.
  • Zombie (defunct) - A process that has exited but whose parent hasn't collected its exit status yet. It holds no memory and cannot be killed — the parent must reap it.
  • Orphan - A process whose parent died first; the kernel re-parents it to PID 1, which reaps it. Normal and harmless.
  • Signal - An asynchronous notification the kernel delivers to a process, such as SIGTERM, SIGINT, or SIGKILL.
  • SIGTERM (15) - The polite default of kill: asks a process to shut down so it can clean up first. Catchable.
  • SIGKILL (9) - The uncatchable kill: the kernel destroys the process with no cleanup. A last resort, not a first move.
  • nohup - Launches a command set to ignore SIGHUP and redirects its output to nohup.out, so it survives the terminal closing.
  • disown - Removes a job from the shell's job table after launch, so the shell won't send it SIGHUP on exit.
  • Job control - The shell's ability to suspend, background, and foreground jobs via Ctrl-Z, bg, fg, and jobs.
