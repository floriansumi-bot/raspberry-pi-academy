You already trust your Raspberry Pi 5 to come alive when you flip the power, and you've poked at logs and services without ever asking who brings the whole machine up. This chapter goes one layer deeper, to the most foundational sequence in the system: the boot chain, and the program at the end of it — systemd, the very first process the kernel starts and the manager of everything that follows. This is genuinely great territory for a Pi owner. Once you can wrap your own script in a service that starts on boot, or replace a fragile cron line with a timer that even catches up missed runs, you have the exact toolkit a home-server project needs. Take your time; this is the chapter where "my Pi just runs my thing now" finally clicks.

The boot chain (and the chicken-and-egg it solves)

Booting is not one big leap. It's a chain of progressively more capable loaders, each just smart enough to find and hand off to the next, ending at PID 1: systemd. On a typical PC the chain looks like this:

1. Firmware (UEFI / BIOS)   - power-on; UEFI reads the FAT EFI System Partition, runs a .efi loader
2. Bootloader (GRUB)        - menu; loads the KERNEL (vmlinuz) + INITRAMFS into RAM; passes the kernel cmdline
3. Kernel                   - decompresses, inits hardware/drivers, mounts the initramfs as a TEMPORARY root
4. initramfs                - tiny RAM root: loads disk/FS drivers, unlocks LUKS, assembles LVM/RAID,
                             finds the REAL root fs, then pivot_root's onto it
5. systemd (PID 1)         - activates default.target, pulling in all dependencies IN PARALLEL
6. Target reached          - login prompt / display manager

The deepest "aha" in the whole sequence is why the initramfs exists. The kernel can't mount your real root filesystem until it has the driver for that disk and that filesystem — but the driver lives on the root filesystem. Chicken, meet egg. The initramfs (a small, self-contained root filesystem that lives in RAM and carries exactly those drivers) breaks the loop: the bootloader loads it into memory first, the kernel uses it to load whatever is needed to reach the real root, and then it pivots onto the real thing and discards the temporary one.

In plain words: The initramfs is a tiny emergency toolkit the kernel keeps in RAM. It contains just enough drivers to find and open your real disk — the disk that holds all the other drivers. Without it the kernel would be locked out of the very filesystem it needs to finish booting.
Note — how your Pi actually boots: A Raspberry Pi has no BIOS, no UEFI, and no GRUB. A Pi 5 starts from a tiny bootloader baked into an EEPROM chip on the board. That firmware reads the FAT boot partition of your microSD card (or NVMe/USB), where it finds config.txt (the Pi's hardware-and-boot settings file), the kernel image, and an initramfs, loads them, and jumps into the kernel — which then hands off to systemd exactly as on a PC. So steps 1 and 2 above are firmware-on-EEPROM plus files-on-the-boot-partition rather than UEFI plus GRUB, but from the kernel onward (steps 3 to 6) your Pi and a PC are identical. We keep the PC chain here because it's worth knowing for any Linux box you meet — just remember your Pi takes the firmware shortcut.

You can watch the whole sequence on your own Pi:

cat /proc/cmdline                 # the exact kernel command line you booted with (root=PARTUUID=... ro ...)
systemd-analyze                   # total boot time, split: firmware | loader | kernel | userspace
systemd-analyze critical-chain    # the dependency chain that actually gated your boot
systemd-analyze blame             # which units took longest
lsinitramfs /boot/initramfs* | head   # what's inside the initramfs (needs initramfs-tools)

/proc/cmdline is a virtual file the kernel fills in with the parameters it was handed at boot — on a Pi that line comes from cmdline.txt on the boot partition rather than from GRUB. systemd-analyze and its sub-commands turn the abstract "boot chain" into concrete numbers you can read and optimise.

Why systemd won (despite the flame wars)

Before systemd, the classic init was SysV init: a set of serial shell scripts run one after another in numbered order. It worked, but it had real, structural limits — and systemd was built to answer each one.

SysV init problem systemd's answer
Serial, slow boot — one script at a time Parallel startup driven by declared dependencies
Couldn't reliably track a daemon's children (a double-fork "lost" them) Every service lives in its own cgroup — systemd sees all its processes and can stop them cleanly
No resource control cgroup-enforced MemoryMax=, CPUQuota=, and more, per service
Logging was ad-hoc text files, each service different journald: structured, indexed logs captured from each service's stdout/stderr automatically
No socket activation / on-demand start .socket units start a service on the first connection to it

You don't have to like systemd to recognise it solved real problems the alternatives didn't. That's why every major distribution — Raspberry Pi OS included — adopted it.

Units: everything is a unit

systemd manages units, and the kind of each unit is given by its filename suffix. Once you internalise this list, most of systemd stops being mysterious:

  • .service — a daemon or process (the kind you'll write most).
  • .socket — a listening socket that can start a service on demand.
  • .target — a named synchronisation point or grouping; targets replace SysV "runlevels" (multi-user.target is roughly the old runlevel 3 / server, graphical.target the old runlevel 5 / desktop).
  • .timer — a scheduled trigger, the modern replacement for cron.
  • .mount / .automount — filesystem mounts.
  • .path — react to a filesystem change.
  • .slice / .scope — cgroup resource groupings.
In plain words: A unit is just one thing systemd knows how to manage, described by a small text file. A service is a unit that runs a program; a target is a unit that is really a labelled checkpoint — "the system has reached this state" — that other units can depend on or be pulled in by.

Here is a minimal but genuinely modern, hardened service. This is the kind of file you'd write to run your own Pi project — say a Python sensor logger or a small web API:

# /etc/systemd/system/myapi.service
[Unit]
Description=My API
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=/usr/local/bin/myapi
Restart=on-failure                 # respawn on crash - a supervisor, for free
DynamicUser=yes                    # ephemeral unprivileged user, auto-created - no manual useradd
AmbientCapabilities=CAP_NET_BIND_SERVICE   # bind :80 without root
NoNewPrivileges=yes
ProtectSystem=strict               # / is mounted read-only to this service
ProtectHome=yes
PrivateTmp=yes                     # its own /tmp, invisible to the rest of the system
MemoryMax=512M                     # cgroup-enforced hard cap

[Install]
WantedBy=multi-user.target         # what `systemctl enable` hooks it into

The file has three sections. [Unit] describes the service and its ordering ("start me after the network is up"). [Service] says how to run it, with the security and resource knobs. [Install] is read only by systemctl enable and decides which target pulls the service in at boot. The Restart=on-failure line alone is worth the price of admission — it gives you crash supervision without writing a single line of babysitting code.

The lifecycle, after you've saved that file, is three commands:

sudo systemctl daemon-reload       # re-read unit files after editing one
sudo systemctl enable --now myapi  # start it now AND on every boot
systemctl status myapi             # state + recent log lines + the cgroup's processes

The key insight: the moment your script lives in a .service file, you get crash recovery, start-on-boot, clean shutdown, resource limits, and automatic logging — all declared in a dozen lines of plain text, with no daemon-writing skill required. That is the single biggest upgrade you can make to a hobby Pi project.

systemctl and journalctl: the power tools

Two commands do most of the day-to-day work. systemctl inspects and controls units; journalctl reads the logs.

systemctl status ssh              # the most useful single command: state, PID, cgroup, last log lines
systemctl list-units --failed     # what's broken right now
systemctl cat nginx               # the EFFECTIVE unit (vendor file + your drop-ins combined)
sudo systemctl edit nginx         # create a drop-in override - NEVER edit vendor files directly
systemd-cgls                      # the cgroup tree, grouped by service

journald is systemd's logging service. Because every service runs in its own cgroup, journald can capture each service's stdout and stderr directly and store them as structured (field-based), indexed logs — not just flat text:

journalctl -u nginx -f             # follow one unit, live
journalctl -u nginx --since "10 min ago"
journalctl -p err -b               # priority error-and-worse, this boot (-b -1 = previous boot)
journalctl -k                      # kernel messages (like dmesg, but persisted across boots)

-u scopes the log to one unit, which turns "find my service's output in a wall of text" into a one-liner. -b limits to the current boot — invaluable on a Pi that you reboot often, or that lost power and you want to know what it said last time (-b -1).

The aha that changes how you write services: because journald grabs stdout and stderr automatically, your program should simply log to stdout. No logfile paths to choose, no log directory to create, no logrotate config, no file permissions to get wrong. The platform handles storage, rotation, and indexing for you. (This is exactly why "12-factor" apps are told to log to stdout — systemd makes it the path of least resistance.)

Timers vs. cron

You've likely met cron for scheduled jobs. systemd timers do the same thing but, for anything service-shaped, do it better. A timer is just a .timer unit that activates a matching .service on a schedule.

Capability cron systemd timer
Calendar schedule yes OnCalendar=daily, *-*-* 04:00:00, and more
Relative / monotonic ("30 min after boot") no OnBootSec=, OnUnitActiveSec=
Ran while the machine was off? silently skipped Persistent=true runs the missed job at next boot
Logging you wire it up yourself automatic, via journald
Runs inside a tracked cgroup no yes (it's just a service)
Dependencies / ordering no yes

That Persistent=true row is the one that matters most on a Pi. Cron's deepest weakness is that a job scheduled for 4 a.m. is simply lost if the machine happened to be powered off then — and a Pi at home is off, asleep, or unplugged far more often than a server. A timer with Persistent=true remembers it missed the run and fires it at the next boot, so your nightly backup actually happens even if "nightly" sometimes lands at 9 a.m. the following day.

systemctl list-timers --all        # every timer: last run, next run, what it triggers

cron is still perfectly fine for simple per-user jobs, and there's no shame in using it. Reach for a timer when you want logging, catch-up runs, dependencies, or resource control — which is most of the time for a real project.

cgroups: the engine underneath

One idea quietly powers half of what makes systemd good: the cgroup (control group). It's a kernel feature that (a) groups processes together so systemd can track and stop all of a service's processes — even ones that tried to escape by double-forking — and (b) limits and accounts their CPU, memory, and I/O. Every systemd service is automatically placed in its own cgroup. Modern systems, your Pi included, use cgroup v2, a single unified hierarchy.

You met cgroups here as systemd's engine. The very same primitive is what containers (Docker and friends) use to box in and limit their workloads — so the MemoryMax=512M line in the service above and a container's memory limit are, underneath, the exact same mechanism viewed from two angles.

Try it on your Pi

  1. Turn a script into a boot service. Write a tiny script that loops and prints the time and temperature every few seconds (use vcgencmd measure_temp). Drop a .service file for it in /etc/systemd/system/ with ExecStart= pointing at your script and Restart=on-failure, then run sudo systemctl daemon-reload and sudo systemctl enable --now mything. Confirm it's alive with systemctl status mything, watch its output with journalctl -u mything -f, then kill the process and watch systemd respawn it. Reboot the Pi and confirm it came back on its own. You now have a proper service.
  2. Replace a cron job with a timer. Take a backup script you'd normally cron, and instead write a backup.service (the job) plus a backup.timer with OnCalendar=daily and Persistent=true. Enable the timer, then check systemctl list-timers to see its next run. To prove the catch-up magic, set the calendar time to a moment in the past while the Pi is off (or shut down past a scheduled run), boot up, and watch the missed job fire immediately — something plain cron silently refuses to do.
  3. Debug a deliberately broken unit. Write a service with three planted faults: a wrong path in ExecStart=, a WorkingDirectory= that doesn't exist, and a missing After= dependency. Then diagnose each one using only systemctl status myunit, journalctl -u myunit -b, and systemd-analyze verify myunit.service. Practise telling apart "the unit file itself is wrong" (systemd refuses to start it) from "the command ran but failed" (a non-zero exit code in the logs). This triage skill is most of real-world systemd work.
  4. Map your Pi's boot. Run systemd-analyze, then systemd-analyze critical-chain, then systemd-analyze blame. Find the single slowest unit on your Pi and the dependency chain that actually gated boot. Finally read /proc/cmdline and explain each kernel parameter on it — remembering that on a Pi this line comes from cmdline.txt on the boot partition, not from GRUB.
Tip: Do the riskier experiments — anything that could leave a service stuck in a crash-loop or a timer misbehaving — on a spare microSD card or a fresh Raspberry Pi OS install, not the Pi you depend on day to day. A broken unit can't brick your hardware, but it can make a boot hang for a couple of minutes, and it's far calmer to learn that on a throwaway card.

Key terms

  • Boot chain — the sequence of ever-more-capable loaders (firmware, bootloader, kernel, initramfs, systemd) that brings a machine up, each handing off to the next.
  • initramfs — a tiny root filesystem the kernel loads into RAM at boot, carrying just enough drivers to find and mount the real root filesystem; it breaks the "driver lives on the disk you can't yet read" chicken-and-egg.
  • EEPROM / boot partition (the Pi's start) — on a Raspberry Pi 5 the bootloader lives in an EEPROM chip and reads config.txt, the kernel, and the initramfs from the FAT boot partition; there is no BIOS, UEFI, or GRUB.
  • systemd — PID 1, the first userspace process; a dependency-driven, parallelised service manager that activates the default target and supervises everything else.
  • unit — any single thing systemd manages, described by a text file and typed by its suffix (.service, .timer, .target, and so on).
  • service — a .service unit that runs a program, with declarative options for restarts, security sandboxing, and resource limits.
  • target — a .target unit acting as a named synchronisation point or grouping; the modern replacement for SysV runlevels (e.g. multi-user.target).
  • journald — systemd's logging service, which captures each service's stdout/stderr via its cgroup and stores structured, indexed, queryable logs read with journalctl.
  • timer — a .timer unit that triggers a service on a schedule; a cron replacement that adds logging, dependencies, and catch-up runs via Persistent=true.
  • cgroup (control group) — the kernel mechanism that groups a service's processes so systemd can track and stop them all, and that enforces CPU/memory/I-O limits; also the foundation of containers.
  • SysV init — the older init system of serial, numbered shell scripts that systemd replaced; serial, hard to supervise, and without resource control.
  • systemd-analyze — the tool that reports boot timing (blame), the gating dependency chain (critical-chain), and unit correctness (verify).
