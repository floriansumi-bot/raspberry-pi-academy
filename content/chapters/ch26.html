By now you can drive your Raspberry Pi 5 with confidence — install software, read logs, fix a stubborn boot. This chapter goes one layer deeper, to the most important boundary in the whole system: the line between your programs and the kernel. Once you can see what a program actually asks the operating system to do, an enormous class of "it just doesn't work" mysteries becomes solvable in seconds. The same tools the professionals use run perfectly on your Pi.

The Kernel Boundary

Your Raspberry Pi runs a full Debian-based Linux (Raspberry Pi OS), and like every Linux system it draws a hard line between two worlds. On one side is userland — every program you run, from ls to a Python script to a web browser. On the other side is the kernel — the privileged core that actually controls the hardware: the CPU, the RAM, the microSD card, the network chip.

The big idea: userland is not allowed to touch hardware, other programs' memory, or kernel data directly. The only doorway is a system call — a controlled, deliberate request that switches the CPU from unprivileged mode into privileged mode, runs a small piece of trusted kernel code on your behalf, and then returns. Every meaningful thing a program does to the outside world — open a file, send a network packet, allocate memory, start another program — ultimately becomes one or more system calls.

In plain words: A system call (or "syscall") is your program politely knocking on the kernel's door and asking it to do something only the kernel is permitted to do. Reading a file, for example, is not something your program does itself — it asks the kernel to do it. If you can watch those knocks, you can see exactly what a program is really doing.

The key insight: once you can observe the syscalls a program makes, you no longer have to guess. The error message might be vague or missing entirely, but the syscall layer never lies — it shows the exact file that wasn't found, the exact socket that refused the connection, the exact moment a program sat down to wait.

Syscall vs. Library Call — Not the Same Thing

This distinction trips up almost everyone at first, and getting it straight tells you which tool to reach for.

  • A library call — like printf, malloc, or strlen — runs inside your own process, in userland. It may eventually make a system call, or it may not. strlen is pure userland arithmetic: it never bothers the kernel. printf formats your text in userland, buffers it, and only later makes a write syscall. malloc hands out memory it already has and only calls the kernel (via brk or mmap) when it needs more.
  • A system call — like write, openat, mmap, or execve — is a request that crosses into the kernel. It costs a mode switch, which is relatively expensive, so libraries deliberately batch them.

The standard C library (libc) is a thin, buffering wrapper that sits on top of the raw syscalls. fopen (buffered, a library function) sits on top of open (the syscall). This is why, if you trace a program that printfs a thousand lines, you see only a handful of write calls — the library quietly collected the output in userland and flushed it to the kernel in big chunks.

your code  ->  libc (printf, malloc, fopen)  ->  SYSCALL (write, mmap, open)  ->  kernel
                  ltrace watches here              strace watches here

Two different tools watch two different layers. ltrace watches the library calls (what functions inside libc your program called). strace watches the system calls (what your program asked the kernel to do). Knowing which layer your question lives in tells you which tool to pick.

strace — Watching What a Program Really Does

strace traces the system calls a process makes, at the exact moment it talks to the kernel. When something "just doesn't work" and the error message is useless, strace shows you the truth. It is, without exaggeration, one of the most useful debugging tools most people have never tried.

It is not installed by default on Raspberry Pi OS, but it is a single command away:

sudo apt install strace lsof

Installs both of this chapter's main tools at once: strace (for watching system calls) and lsof (for listing open files, which we meet shortly). Both are small and completely safe to have on your Pi.

Here are the patterns you will use again and again:

strace ls                            # every syscall that 'ls' makes
strace -f ./app                      # -f: follow forked child processes too
strace -e trace=openat,stat ./app    # only the file-opening syscalls
strace -e trace=network curl host    # only socket / connect / send / recv
strace -p 1234                       # ATTACH to an already-running process (PID 1234)
strace -c ls                         # summary: which syscalls dominate, time spent
strace -f -o trace.txt ./app         # save the full trace to a file

The -e trace= filter is what makes strace usable in practice — an unfiltered trace is a firehose. The -p form is special: it lets you peek inside a process that is already running (for example, one that appears frozen) without restarting it. Use Ctrl + C to detach.

Three killer use cases

  • "It can't find its config file." Run strace -e trace=openat app 2>&1 | grep -i config and you will see exactly which paths the program tried, in order. A line ending in ENOENT means "no such file" — so you can see precisely where it looked and why it gave up. No more guessing where a tool keeps its settings.
  • "It hangs — is it busy or stuck?" Attach with strace -p PID. If the process is parked inside read, futex, poll, or accept, it is waiting on something (input, a lock, the network) — not computing. If instead it is rattling through a stream of syscalls, it is genuinely working. This one trick replaces hours of staring at a frozen terminal.
  • "Permission denied — but on what?" The failing syscall names the exact file or socket, and the error code EACCES tells you it was a permissions problem. You stop guessing and go straight to the offending path.
Careful: Attaching strace to a process briefly slows it down, because every syscall now has to be reported. That is fine for debugging on your Pi, but avoid tracing a busy production service unless you have to — and never leave a trace running on something time-sensitive. Tracing a program you do not trust is also a way to learn what it is quietly doing.

The Observability Toolkit — Match the Symptom to the Layer

The real senior-engineer skill is not memorising commands — it is asking "which layer is lying to me?" and reaching for the matching tool. Keep this table handy; it turns a vague symptom into a specific tool.

Layer Tool Reach for it when…
System calls (the kernel boundary) strace "What is it really doing? Why does it fail or hang?"
Library / function calls ltrace "Which libc/OpenSSL function returned the bad value?" (flaky on modern, statically built binaries)
Open files, sockets, ports lsof "Who is holding this file or port?" "What is eating my disk?"
Live process internals /proc/<pid>/ Memory map, open file descriptors, state, what it is sleeping on
CPU hotspots perf "Where is the CPU time actually going?"
Kernel-level tracing bpftrace / eBPF "Trace every file open or network event, system-wide, live"
Kernel messages dmesg OOM kills, hardware/driver errors, undervoltage, segfaults
Service logs journalctl What a systemd background service logged

lsof — "list open files" (and on Linux, almost everything is a file)

On Linux, files, sockets, and devices are all reached through the same "open file" mechanism, so a single tool can answer a surprising range of questions:

lsof -i :443              # which process is using / listening on port 443
lsof -p 1234              # every file and socket that process 1234 has open
lsof /var/log/app.log     # who has this file open (why won't it unmount?)
lsof +L1                  # DELETED-but-still-open files — the disk-space mystery culprit

lsof -i answers "what is using this port?" — invaluable when a server on your Pi reports the address is already in use. lsof +L1 lists files that have been deleted from disk but are still held open by a running process, which is the key to one of the most baffling problems in all of Linux.

In plain words: A file descriptor is just a numbered handle the kernel gives your program when it opens a file or a network connection. lsof lists those handles for every process, so you can see exactly what each program is touching.

The classic disk-space mystery: someone deletes a huge log file with rm, yet df still reports the disk as full while du finds nothing taking up space. What happened? A process still has the deleted file open. On Linux a file's data survives until the last open handle closes — deleting the name is not the same as freeing the data. lsof +L1 finds the guilty process; restarting it closes the handle and the space comes back instantly. This is a real production incident you can now diagnose in under a minute, and it is very much a Pi problem too, where the microSD card has limited room.

/proc/<pid>/ — a live X-ray of any process

Linux exposes the kernel's view of every running process as a set of virtual files under /proc. They are not real files on the card — reading them asks the kernel for live information:

cat  /proc/1234/status                  # memory, threads, state, user IDs
ls -l /proc/1234/fd/                     # every open file descriptor, as a symlink
cat  /proc/1234/maps                     # full memory layout: libraries, heap, stack
cat  /proc/1234/cmdline | tr '\0' ' '    # the exact command line it was started with
cat  /proc/1234/wchan                    # the kernel function it is currently sleeping in

/proc/<pid>/wchan pairs beautifully with strace -p: when a process is stuck, wchan names the exact kernel function it is waiting inside, telling you what it is blocked on without reading a single line of source code. (Replace 1234 with the real process ID, which you can find with htop or pidof.)

dmesg — the kernel's own diary

dmesg -T -w                 # follow kernel messages live, with human timestamps
dmesg -T | grep -i oom      # did the kernel's memory killer strike? (see below)

dmesg prints the kernel's internal log. It is the first place to look for "the kernel killed my process," USB or microSD card errors, undervoltage warnings on the Pi, driver problems, and segfaults. The -T flag turns raw timestamps into readable dates.

perf and eBPF — The Modern Frontier

Two more tools are worth knowing exist, even if you do not master them today:

  • perf is a sampling profiler backed by the CPU's own hardware counters. perf top shows the hottest functions live; perf record -g ./app followed by perf report gives a call-graph profile you can even turn into a flame graph. It answers "where is my CPU time actually going?" — and the answer is often a surprise, which is exactly why measuring beats guessing.
  • eBPF (driven by bpftrace) lets you run tiny, safety-checked programs inside the kernel, attached to events, with almost no overhead and no rebooting. It powers most modern observability tools.
# Every file opened, system-wide, live — with the program that opened it:
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args->filename)); }'

You do not need to learn eBPF now — just know it is how professionals answer questions that used to require patching and recompiling the kernel. On a Pi it is a fun way to watch, in real time, every file the whole system opens.

Virtual Memory and the OOM Killer

This last section is especially relevant on a Raspberry Pi, because a Pi has modest RAM (commonly 4 GB or 8 GB), and running out of memory behaves in a way that confuses almost everyone the first time they hit it.

Every pointer your program sees is a (useful) lie

Programs never touch physical RAM addresses directly. Each process gets its own virtual address space, and the CPU's memory unit translates those virtual addresses to physical pages on the fly, separately for every process. This buys you three things:

  • Isolation for free — process A's address 0x1000 and process B's 0x1000 point at different physical memory. One program cannot read another's memory just by guessing an address.
  • Demand paging — memory you "allocate" is not backed by real RAM until you actually touch it. The kernel hands out promises and only commits a real page on first use.
  • Overcommit — because of demand paging, Linux happily lets programs allocate more total memory than physically exists, betting they will not use it all at once. Usually that bet pays off. Sometimes it doesn't.
cat /proc/<pid>/status    # VmRSS = real RAM in use; VmSize = virtual size (the "promise")
cat /proc/<pid>/maps      # the full virtual layout: code, libraries, heap, stack

In /proc/<pid>/status, two numbers matter. VmSize is the virtual size — the total memory the process has reserved, most of which may never be touched. VmRSS is the resident set size — the actual physical RAM the process is using right now.

The key insight: VmSize (virtual) is almost always much larger than VmRSS (real). A process reporting 2 GB of "virtual" memory might be using only 80 MB of actual RAM. Beginners panic at the big virtual number; the one that matters for "am I about to run out of RAM?" is RSS.

The OOM killer — what happens when the bet fails

When the system genuinely runs out of memory (RAM plus swap), the kernel does something dramatic to save itself: it invokes the Out-Of-Memory killer. The OOM killer scores every process by its oom_score — roughly, how much memory killing it would free — and then kills the highest scorer. Your program did not crash of its own accord. The kernel deliberately executed it to keep the whole machine alive.

dmesg -T | grep -i 'killed process'      # the OOM killer's verdict and its victim
cat /proc/<pid>/oom_score                 # a process's current score
echo -1000 > /proc/<pid>/oom_score_adj    # protect a critical process (run as root)

dmesg records every OOM kill with the name and PID of the victim, so it confirms the diagnosis instantly. The oom_score_adj file lets you bias the decision — a very negative value tells the kernel "please don't pick this one," which is handy for protecting an important service on a memory-tight Pi.

Two ways to give your Pi more breathing room before the OOM killer ever fires: swap extends RAM onto the microSD card (slow, but it buys time and prevents premature kills), and zram is a compressed, RAM-backed swap that is much faster — often the better choice on a Pi, since it avoids hammering the card. In containers, hitting a cgroup memory.max limit triggers the same mechanism, scoped to just that container.

The aha that closes the loop: "My process just vanished — no error, no traceback, exit code 137" is almost always the OOM killer. The 137 comes from 128 + 9: the process was terminated by signal 9 (SIGKILL), which is exactly how the OOM killer ends a process. Whenever a program disappears silently on your Pi — especially something memory-hungry like a large build, an image generator, or a big data job — your very first move is dmesg -T | grep -i oom. It connects straight back to the start of this chapter: when in doubt, ask the kernel.

Try it on your Pi

  1. Trace which config a program opens. Pick a program that reads a config file — git, curl, or ssh are perfect. Run strace -f -e trace=openat git status 2>&1 | grep -i config and watch it list every path it tries, in order. Now rename one of those files and run it again: you will see the failed attempt end in ENOENT. You will never again wonder where a tool looks for its settings.
  2. Diagnose a hang. In one terminal run sleep 600 (a program that does nothing but wait). In another, find its PID with pidof sleep, then run strace -p PID and cat /proc/PID/wchan. You will see it parked in a waiting syscall — proof, without reading any source code, that it is blocked rather than busy.
  3. Solve the phantom disk-space bug. Start a process writing to a log (for example, ping raspberrypi.com > /tmp/big.log &), then rm /tmp/big.log while it is still running. Notice that df -h still shows the space as used while the file no longer appears. Run sudo lsof +L1 to find the deleted-but-open file, then stop that process to reclaim the space. You have just solved a real production incident.
  4. Trigger and read an OOM kill. Carefully — and only on a Pi you don't mind rebooting — run a deliberate memory hog such as tail /dev/zero (it allocates forever). When the Pi runs out of memory the kernel will kill it. Confirm with dmesg -T | grep -i oom and find the exit code with echo $? (look for 137). Then read about giving the Pi more headroom with zram.
Careful: The fourth project deliberately starves your Pi of memory. It can make the system briefly unresponsive and may kill other programs, so close anything important first, save your work, and be ready to reboot. Never run a memory-exhaustion test on a Pi doing real work.

Key terms

  • System call (syscall) — a controlled request from a userland program to the kernel; the only legitimate way for a program to reach hardware, files, the network, or more memory.
  • Userland vs. kernel — userland is every ordinary program; the kernel is the privileged core that controls the hardware. The boundary between them is crossed only by system calls.
  • Library call — a function such as printf or malloc that runs inside your own process and may or may not make a syscall; libc buffers and batches calls to the kernel.
  • strace — a tool that traces the system calls a process makes, revealing exactly what it asks the kernel to do; ideal for "why does it fail or hang?"
  • ltrace — the library-call equivalent of strace, showing which libc/library functions a program calls (less reliable on modern static binaries).
  • lsof — "list open files"; shows which process holds a file, socket, or port, and finds deleted-but-still-open files with +L1.
  • /proc — a virtual filesystem exposing live, per-process kernel data: memory maps, open file descriptors, state, and what a process is sleeping on.
  • File descriptor — the numbered handle the kernel gives a process for each open file or socket.
  • Virtual memory / demand paging — each process has its own address space; allocated memory is backed by real RAM only when first touched.
  • RSS vs. virtual size — VmRSS is the real physical RAM a process uses now; VmSize is the larger virtual reservation. RSS is the number that matters for running out of memory.
  • Overcommit — Linux allowing programs to allocate more memory than physically exists, betting they won't use it all at once.
  • OOM killer — the kernel's Out-Of-Memory killer, which terminates the highest-scoring process when memory runs out; a process killed this way exits with code 137 (128 + signal 9).
  • swap / zram — ways to extend RAM: swap onto the microSD card (slow), or compressed RAM-backed zram (fast) — useful headroom on a memory-tight Pi.
  • dmesg — the kernel's message log; the first place to confirm an OOM kill, hardware error, or undervoltage on the Pi.
