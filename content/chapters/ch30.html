A sliver of plastic and a glittering dome of glass, pulled from a dead security light in the e-waste box, can still do one thing brilliantly: notice when a warm body moves nearby. In this project you will give that salvaged PIR motion sensor a second life as a motion-activated alarm — one that flashes an LED, sounds a buzzer, stamps the time in a logbook, and can be armed or disarmed from the keyboard. Along the way you will learn the Python idea that powers almost every interactive program in the world: event-driven programming — writing little functions called callbacks that the computer runs automatically the moment something happens.

What You'll Build & Learn

By the end of this chapter you will have a working intruder alarm built almost entirely from salvaged parts, and you will understand a new and powerful way of structuring programs.

Here are the fundamentals this project teaches, named plainly so you know exactly what you are practising:

Python fundamentals

  • Event-driven programming. Instead of a program that marches top-to-bottom and then stops, you write code that waits and reacts. The sensor decides when things happen; your job is to say what happens.
  • Callbacks — the functions when_motion and when_no_motion. A callback is a function you hand to another object so it can "call you back" later, at the right moment.
  • Blocking waits with wait_for_motion() — pausing your program at one line until motion arrives.
  • Organising code into functions and modules. You will split your program into small, well-named functions and then move the reusable pieces into a separate module (a second .py file) that you import.
  • Counting events with a simple counter variable and the global keyword.

Electronics fundamentals

  • The PIR motion sensor (the common HC-SR501) and the gpiozero MotionSensor class.
  • 3.3 V-safe digital outputs. The PIR's OUT pin already speaks 3.3 V, so — unlike the HC-SR04 ultrasonic sensor from Chapter 28 — it connects directly to a GPIO pin with no voltage divider. Knowing which sensors need protection and which do not is a core safety skill.
  • Combining outputs: driving an LED and a buzzer together as the alarm's "siren".

What Is Event-Driven Programming?

Every program you have written so far has probably run like a recipe: do step 1, then step 2, then step 3, and finish. That style is called sequential programming, and it is perfect for tasks with a clear beginning and end.

But an alarm is different. An alarm spends almost all of its life doing nothing — quietly waiting. Then, at an unpredictable moment, something happens, and it must react instantly. You cannot write that as a fixed list of steps, because you do not know in advance when the steps should run.

In plain words: An event is "something that happened" — a button press, a key tap, a sensor noticing motion. Event-driven programming means you write small functions that say what to do when each event happens, then you let the program sit and wait. The events drive the program, instead of the program marching through a fixed list.

The function you hand over to be run later is called a callback. The name is wonderfully literal: you give your function to gpiozero and effectively say, "don't run this now — call me back when motion happens." You met this idea briefly in Chapter 12 with a button's when_pressed. Here we lean into it properly.

A tiny isolated example first

Before wiring anything, let's see the shape of an event-driven program with the smallest possible example. You can read this even without the hardware connected yet — it shows the pattern, which is the important part.

from gpiozero import MotionSensor
from signal import pause

pir = MotionSensor(4)

def someone_moved():
    print("Motion detected!")

def all_clear():
    print("All quiet now.")

pir.when_motion = someone_moved
pir.when_no_motion = all_clear

pause()

Line 1 — from gpiozero import MotionSensor: Pulls in the ready-made gpiozero object for PIR motion sensors. You do not need to install anything — gpiozero is preinstalled on Raspberry Pi OS Bookworm.

Line 2 — from signal import pause: Brings in pause(), which keeps an event-driven program alive and waiting. Without it the program would reach the bottom and exit instantly, before any motion could ever be noticed.

Line 4 — pir = MotionSensor(4): Creates a sensor object listening on GPIO 4 (physical pin 7). The number 4 is the GPIO (BCM) number, not the physical position on the header.

Lines 6–7 — def someone_moved():: Defines a function — a named block of instructions. Crucially, defining it does not run it. We are simply describing what should happen later.

Lines 9–10 — def all_clear():: A second function, for when the motion stops.

Line 12 — pir.when_motion = someone_moved: This is the heart of event-driven programming. We hand the function someone_moved to the sensor. Notice there are no parentheses after the name — someone_moved, not someone_moved(). With parentheses you would call the function right now; without them you are pointing at it, so gpiozero can call it back later.

Line 13 — pir.when_no_motion = all_clear: Same idea, registering the "all clear" callback.

Line 15 — pause(): Sits here forever, letting the sensor watch in the background and fire your callbacks whenever motion starts or stops. Press the red Stop button in Thonny (or Ctrl+C in a terminal) to end it.

Careful: A common beginner slip is writing pir.when_motion = someone_moved() with parentheses. That runs the function immediately, once, and then hands its return value (usually None) to the sensor — so nothing ever happens on real motion. Always register a callback by name, with no parentheses.

The other style: a blocking wait

Callbacks are not the only way. Sometimes you want your program to stop at one exact line and wait for motion before going on. gpiozero gives you wait_for_motion() for precisely that:

from gpiozero import MotionSensor

pir = MotionSensor(4)

print("Waiting for motion...")
pir.wait_for_motion()
print("Got it! Something moved.")

Line 6 — pir.wait_for_motion(): This line blocks — the program freezes here, doing nothing else, until the sensor detects motion. Only then does it move on to line 7. This is called a blocking call because it blocks the rest of the program from running until its condition is met.

In plain words: Blocking means "wait right here until I'm done". wait_for_motion() is simple and reads top-to-bottom, but your program can only wait for one thing at a time. Callbacks (when_motion) are more flexible: the sensor watches in the background while your program gets on with other jobs. Our alarm will use callbacks.

From the E-Waste Pile: Salvaging a PIR

PIR sensors are one of the most rewarding things to rescue from the e-waste box, because they are everywhere. The little white plastic boxes that switch on a porch light when you walk up the path, cheap battery alarms, motion-activated toys and ornaments — almost all of them hide a PIR module that is identical, or nearly identical, to the HC-SR501 you can buy new.

In plain words: PIR stands for Passive Infrared. Everything warm — including you — glows faintly in infrared light that your eyes cannot see. The sensor is "passive" because it does not send anything out; it simply watches for a change in that infrared glow as a warm body moves across its view. That is why a PIR detects movement but not a person standing perfectly still.

Where to find one

  • Dead motion-sensor security lights — the classic source. The white dome you see on the front is the PIR's lens. The light may have failed, but the sensor module behind it usually still works.
  • Old burglar-alarm PIR units — the wall-corner boxes. Often still perfectly good; the panel they reported to is the dead part.
  • Motion-activated novelty toys, soap dispensers, and night-lights.

How to recognise the module

Once you open the plastic case (only ever low-voltage, battery or USB-powered items — see the warning below), look for a small circuit board carrying a white, faceted, half-dome lens about the size of a thumbnail. This lens is called a Fresnel lens; it divides the sensor's view into segments so movement registers more strongly. Underneath you will usually find a board labelled HC-SR501 (or a near clone) with three pins. Those three pins are the whole story:

Pin markingWhat it isWhere it goes
VCC (sometimes + or 5V)Power inA 5 V pin on the Pi
OUT (sometimes S or SIG)The signal — goes HIGH when motion is seenDirectly to a GPIO pin
GND (sometimes − or G)Ground / returnA GND pin on the Pi
Careful: Only ever open battery-powered or low-voltage USB gadgets. Never open anything that plugs into the mains — a security floodlight wired to your house mains, for example, must be left to a qualified electrician. Mains-powered devices can hold a dangerous charge in their capacitors even when unplugged. If you are unsure, leave it shut and pick a battery-powered item instead. When in doubt, throw it out.
Tip: Even a brand-new HC-SR501 costs very little, so if your salvaged module misbehaves it is no disaster. But test the salvaged one first — most work perfectly. You will also reuse an LED and a buzzer from the earlier chapters' salvage hauls (a mouse LED and a toy buzzer are ideal).

Meet the HC-SR501

The HC-SR501 has a couple of features worth knowing before you build, because they catch out almost everyone the first time.

The warm-up period

When you first power up a PIR, it needs roughly 30 to 60 seconds to settle. During this warm-up it calibrates itself to the room's background infrared and may fire falsely. This is completely normal. The polite thing to do is keep your alarm "disarmed" for the first minute — and our program will do exactly that.

The two orange potentiometers

On the board, next to the pins, you will usually find two small orange dials you can turn with a tiny screwdriver. These are potentiometers ("pots" for short) — adjustable resistors.

  • Sensitivity — how far away motion is detected (roughly 3 to 7 metres). Turn it down if the alarm triggers from across the whole room when you only want the doorway.
  • Time delay — how long OUT stays HIGH after motion before it resets (from a couple of seconds up to several minutes). For testing, turn this fully anticlockwise to its shortest setting so the sensor resets quickly and you are not waiting around.
Note: Many HC-SR501 boards also have a tiny jumper that selects "repeat trigger" vs "single trigger" mode. For an alarm, leave it on repeat trigger (often marked H) so continued movement keeps OUT held HIGH. gpiozero copes with either, but repeat mode behaves more naturally for an alarm.

Parts & Wiring

What you need

  • A Raspberry Pi 5 running Raspberry Pi OS Bookworm
  • 1 × PIR motion sensor (HC-SR501 — salvaged or new)
  • 1 × LED (any colour — red suits an alarm), salvaged or new
  • 1 × 330 Ω resistor (orange-orange-brown-gold) for the LED
  • 1 × active buzzer (the kind that just needs on/off — salvaged from a toy is ideal)
  • 1 × breadboard
  • Female-to-male jumper wires (about 7) and a couple of male-to-male wires
In plain words: An active buzzer has its own tone-generating circuit inside, so you only have to switch it on and off — perfect for gpiozero's Buzzer object. (A passive buzzer needs you to feed it a tone; that is a different object, TonalBuzzer.) A small buzzer draws little enough current to drive straight from a GPIO pin. A real loudspeaker would not — that needs a transistor — but a buzzer is fine.
Careful: Power off and unplug your Pi before wiring anything. Shut down from the desktop (Raspberry Pi menu → Shutdown), wait for the green light to go out, then remove the power lead. Only reconnect power once you have checked every connection. Wiring a live header is the most common way to damage a GPIO pin.

The key safety fact: no divider needed

Here is the single most important electronics point in this chapter. The HC-SR501's OUT pin already outputs 3.3 V logic when it detects motion, even though the sensor is powered from 5 V. That means OUT is safe to connect directly to a GPIO pin.

Contrast this with the HC-SR04 ultrasonic sensor from Chapter 28, whose ECHO pin outputs a full 5 V that would damage a 3.3 V GPIO — so that one needs a resistor voltage divider. The PIR does not. Two sensors, both powered from 5 V, but only one needs protection on its signal pin. Knowing the difference is exactly the kind of judgement that keeps your Pi alive.

Careful: Power the PIR from 5 V (its VCC needs 5 V to work), but never let that 5 V touch a GPIO pin directly. Only the OUT pin — which is already 3.3 V — goes to a GPIO. Double-check you have VCC on 5 V and OUT on the GPIO, and not the other way round.

Step-by-step wiring

Careful: The Pi must be fully shut down and unplugged for every step below. Do not reconnect power until the final step.
  1. Plant the breadboard ground rail. Run a male-to-male jumper from a Pi GND pin (physical pin 6) to the breadboard's blue (−) power rail. Everything's ground will return here.
  2. Wire the LED. Push the LED into the board with its long leg (anode, +) and short leg (cathode, −) in separate rows. Connect a 330 Ω resistor from the long-leg row, then a jumper from there to GPIO 17 (pin 11). Connect the short leg to the blue (−) rail.
  3. Wire the buzzer. An active buzzer usually has a + marked terminal (often the longer leg). Connect + to GPIO 27 (pin 13) and the other terminal to the blue (−) rail.
  4. Wire the PIR power. Connect PIR VCC to a 5 V pin (physical pin 2) and PIR GND to the blue (−) rail.
  5. Wire the PIR signal — the careful one. Connect PIR OUT straight to GPIO 4 (pin 7). No resistor, no divider. Just confirm it really is the OUT pin and not VCC.
  6. Set the pots for testing. Turn the time-delay pot fully anticlockwise (shortest), and the sensitivity pot to roughly the middle. Set the jumper to repeat-trigger (H) if present.
  7. Inspect everything twice. Trace each wire from end to end. Confirm VCC is on 5 V and OUT is on the GPIO — swapping them is the classic mistake.
  8. Only now reconnect power and let the Pi boot to the desktop. Remember the PIR will need its 30–60 s warm-up.

Building the Alarm Step by Step

We will build the program in layers, so each new idea lands on its own. First a bare callback alarm, then we add a logbook and a counter, then we organise it into functions, and finally we split it into a reusable module and add arm/disarm control.

Version 1: the siren callbacks

Open Thonny (Raspberry Pi menu → Programming → Thonny) and type this first version:

from gpiozero import MotionSensor, LED, Buzzer
from signal import pause

pir = MotionSensor(4)
led = LED(17)
buzzer = Buzzer(27)

def sound_alarm():
    print("INTRUDER!")
    led.on()
    buzzer.on()

def stop_alarm():
    print("All clear.")
    led.off()
    buzzer.off()

pir.when_motion = sound_alarm
pir.when_no_motion = stop_alarm

print("Arming... (give the PIR up to a minute to settle)")
pause()

Line 1 — from gpiozero import MotionSensor, LED, Buzzer: Imports all three components we need in one line: the PIR, the LED, and the active buzzer.

Lines 4–6 — creating the objects: One object per piece of hardware, each tied to its GPIO number. Buzzer(27) drives an active buzzer with simple on() / off() control.

Lines 8–11 — def sound_alarm():: A function that is the alarm going off: it prints a warning, lights the LED, and switches on the buzzer. Grouping these three actions into one named function is the first step of organising code — the name says what it does.

Lines 13–16 — def stop_alarm():: The opposite: turns the siren off when motion stops.

Lines 18–19 — registering the callbacks: We hand sound_alarm to when_motion and stop_alarm to when_no_motion. No parentheses — we are pointing at the functions, not calling them.

Line 22 — pause(): Keeps the program alive so the sensor can fire the callbacks. Save the file as alarm.py and run it; after the warm-up, wave a hand and the LED and buzzer should burst into life.

Version 2: logging the time and counting events

An alarm that forgets everything the instant it happens is not much of an alarm. Let's stamp every trigger with the time and keep a running count of how many times the alarm has fired. To get the current time we use Python's built-in datetime module; to count, we use a variable.

from gpiozero import MotionSensor, LED, Buzzer
from datetime import datetime
from signal import pause

pir = MotionSensor(4)
led = LED(17)
buzzer = Buzzer(27)

alarm_count = 0

def log(message):
    stamp = datetime.now().strftime("%Y-%m-%d %H:%M:%S")
    line = f"[{stamp}] {message}"
    print(line)
    with open("alarm_log.txt", "a") as logfile:
        logfile.write(line + "\n")

def sound_alarm():
    global alarm_count
    alarm_count = alarm_count + 1
    led.on()
    buzzer.on()
    log(f"INTRUDER! (event #{alarm_count})")

def stop_alarm():
    led.off()
    buzzer.off()
    log("All clear.")

pir.when_motion = sound_alarm
pir.when_no_motion = stop_alarm

log("Alarm armed.")
pause()

Line 2 — from datetime import datetime: Imports Python's datetime object, which can tell us the current date and time. It is built in — nothing to install.

Line 9 — alarm_count = 0: Creates a counter, starting at zero. Because it sits outside any function, it is a module-level (global) variable that all the functions can see.

Lines 11–16 — def log(message):: A reusable helper. datetime.now() grabs the moment; .strftime("%Y-%m-%d %H:%M:%S") formats it as a tidy timestamp like 2026-06-23 14:09:02. We build the line with an f-string, print it, and append it to a file.

Line 15 — with open("alarm_log.txt", "a") as logfile:: Opens a file in append mode ("a"), so new lines are added to the end without erasing what is already there. The with block closes the file automatically when it finishes.

Line 19 — global alarm_count: Tells Python that inside this function we mean the module-level alarm_count, not a brand-new local one. Without this line, alarm_count = alarm_count + 1 would error, because Python would treat alarm_count as a fresh local variable that has not yet been given a value.

Line 20 — alarm_count = alarm_count + 1: Adds one to the counter each time the alarm fires — this is counting events.

Line 23 — log(f"INTRUDER! (event #{alarm_count})"): Calls our helper to print and save a timestamped, numbered alert.

In plain words: A global variable is one defined at the top level of your file, outside every function. Functions can read it freely, but to change it they must first declare global name. This is Python's way of making sure you don't accidentally reassign an outer variable by mistake.

Organising Code into a Module

Our file is growing. The log() helper is genuinely useful — we would happily reuse it in other projects. This is the moment to learn a real software habit: moving reusable code into its own module.

In plain words: A module is just a Python file (a .py) whose functions and variables you can use from another file with import. You have been importing modules all along — gpiozero and datetime are modules. Now you will write your own.

Create a new file called alarm_tools.py in the same folder, containing just the reusable helpers:

# alarm_tools.py — reusable helpers for our alarm projects
from datetime import datetime

LOG_FILE = "alarm_log.txt"

def now_stamp():
    """Return the current time as a tidy string."""
    return datetime.now().strftime("%Y-%m-%d %H:%M:%S")

def log(message):
    """Print a timestamped message and append it to the log file."""
    line = f"[{now_stamp()}] {message}"
    print(line)
    with open(LOG_FILE, "a") as logfile:
        logfile.write(line + "\n")

Line 1 — the comment: A note for human readers. Python ignores anything after #.

Line 4 — LOG_FILE = "alarm_log.txt": A constant holding the filename in one place, so we never have to retype it. Naming it in CAPITALS is a common convention for "this is a fixed setting".

Lines 6–8 — def now_stamp():: Returns the formatted time. The triple-quoted line just below the def is a docstring — a short description of what the function does, which editors can show as a hint.

Lines 10–15 — def log(message):: The same logging helper as before, now living in its own module so any program can import it.

Now your main alarm file becomes shorter and clearer, because it borrows log from the module:

# alarm.py — the main program
from gpiozero import MotionSensor, LED, Buzzer
from signal import pause
from alarm_tools import log

pir = MotionSensor(4)
led = LED(17)
buzzer = Buzzer(27)

alarm_count = 0

def sound_alarm():
    global alarm_count
    alarm_count += 1
    led.on()
    buzzer.on()
    log(f"INTRUDER! (event #{alarm_count})")

def stop_alarm():
    led.off()
    buzzer.off()
    log("All clear.")

pir.when_motion = sound_alarm
pir.when_no_motion = stop_alarm

log("Alarm armed.")
pause()

Line 4 — from alarm_tools import log: Imports the log function from your own module, exactly the way you import from gpiozero. The only requirement is that alarm_tools.py sits in the same folder.

Line 14 — alarm_count += 1: A tidy shorthand for alarm_count = alarm_count + 1. The += operator means "add to and store back".

The rest: reads almost like plain English now, because the messy timestamp-and-file detail is tucked away in the module. That is the whole point of organising code — each file does one clear job.

Tip: When you import your own module, Python may create a folder called __pycache__ next to it. That is just a cache of the compiled module to make future imports faster — it is harmless and you can ignore it.

Arming and Disarming

A real alarm can be switched off — otherwise you can never walk past your own sensor. We will add an armed flag: a simple True/False variable that the callbacks check before sounding. We will also use the keyboard to toggle it, and the PIR's warm-up minute will start disarmed automatically.

Because we want to type commands and let the sensor fire callbacks in the background, this version uses an input() loop in the main program instead of pause(). The callbacks still run in the background whenever motion happens.

# alarm.py — arm/disarm version
from gpiozero import MotionSensor, LED, Buzzer
from alarm_tools import log

pir = MotionSensor(4)
led = LED(17)
buzzer = Buzzer(27)

armed = False
alarm_count = 0

def sound_alarm():
    global alarm_count
    if not armed:
        return
    alarm_count += 1
    led.on()
    buzzer.on()
    log(f"INTRUDER! (event #{alarm_count})")

def stop_alarm():
    led.off()
    buzzer.off()
    if armed:
        log("Movement stopped.")

pir.when_motion = sound_alarm
pir.when_no_motion = stop_alarm

print("Commands: 'arm', 'disarm', 'count', 'quit'")
log("System started (disarmed). PIR warming up...")

while True:
    command = input("alarm> ").strip().lower()
    if command == "arm":
        armed = True
        log("ARMED.")
    elif command == "disarm":
        armed = False
        led.off()
        buzzer.off()
        log("Disarmed.")
    elif command == "count":
        print(f"Alarm has triggered {alarm_count} time(s).")
    elif command == "quit":
        log("Shutting down.")
        break
    else:
        print("Unknown command. Try arm / disarm / count / quit.")

Line 9 — armed = False: A boolean flag holding the alarm's state. Starting at False means the system is harmlessly disarmed while the PIR warms up.

Lines 14–15 — if not armed: return: The first thing sound_alarm does is check the flag. If the alarm is disarmed, return leaves the function immediately, so no siren and no count. This is how one variable acts as a master switch over an event callback.

Line 24 — if armed: inside stop_alarm: We only bother logging "movement stopped" when the system was actually armed, to keep the log meaningful.

Line 34 — command = input("alarm> ")...: input() waits for you to type a line and press Enter. .strip() trims stray spaces and .lower() makes the command case-insensitive, so ARM and arm both work.

Lines 35–48 — the if/elif/else ladder: Each branch handles one command. arm and disarm flip the flag; count reports the total; quit uses break to leave the while loop and end the program neatly.

Note on the background: while you sit at the input() prompt, gpiozero is still watching the sensor on a separate thread, so motion still fires sound_alarm — it simply does nothing unless armed is True.

Note: Notice we did not need global armed inside the while loop, because that loop lives at the top level of the file — the same place armed is defined. We do need global alarm_count inside sound_alarm, because that assignment happens inside a function.

Running It

  1. Save both files in the same folder: alarm_tools.py and alarm.py. In Thonny, File → Save for each.
  2. Run alarm.py with the green Run button (or press F5). The shell at the bottom shows the prompt and the start-up log line.
  3. Wait out the warm-up. Leave it disarmed for about a minute while the PIR settles. Resist the urge to wave at it yet.
  4. Arm it. Type arm and press Enter. Now walk into the sensor's view — the LED should light and the buzzer sound, and a timestamped INTRUDER! line appears.
  5. Disarm it. Type disarm to silence the system so you can move freely.
  6. Check the tally. Type count to see how many times it triggered, then quit to stop.
  7. Read the logbook. Open a terminal and view your records with the command below.
cat alarm_log.txt

cat alarm_log.txt: Prints the whole log file to the terminal, so you can see every timestamped event your alarm recorded. cat simply means "show me the contents of this file".

Make It Your Own

You now have a complete, modular, event-driven alarm. Here are four ways to take it further:

  • Flash instead of glare. Replace led.on() with led.blink() in sound_alarm so the warning light pulses like a real alarm beacon. Remember to led.off() in stop_alarm.
  • Add a quiet "armed" indicator. Use a second, green LED that is lit whenever armed is True, so you can tell the system's state at a glance.
  • Count only real intrusions. Add a few seconds of "cool-down" so repeated motion within, say, five seconds counts as one event — using datetime to compare the time since the last trigger.
  • Send yourself an alert. Once you are comfortable, have sound_alarm also write to a file your phone can read, or — in the next chapter — surface the last alarm time on a live web dashboard you can check from anywhere in the house.
Tip: The arm/disarm flag pattern you wrote here — one boolean that every callback checks first — is exactly how real software gates behaviour: feature switches, "do not disturb" modes, pause buttons. You have learned a genuinely professional idea dressed up as a fun alarm.

Key terms

  • Event-driven programming - A style where the program waits and reacts to events (like motion) instead of running a fixed top-to-bottom list of steps.
  • Event - Something that happens at an unpredictable time, such as motion being detected or a key being pressed.
  • Callback - A function you hand to another object so it can call it back when an event occurs; registered by name with no parentheses (e.g. pir.when_motion = sound_alarm).
  • Blocking call - A line such as wait_for_motion() that pauses the whole program until its condition is met.
  • Module - A Python file whose functions and variables another file can use via import; you wrote your own (alarm_tools.py).
  • Global variable - A variable defined at the top level of a file; to reassign it inside a function you must first declare global name.
  • PIR sensor - Passive Infrared sensor; detects movement by sensing changes in the infrared (heat) glow of warm bodies.
  • HC-SR501 - The common, inexpensive PIR module with VCC/OUT/GND pins, a Fresnel lens, two adjustment pots, and a 30–60 s warm-up.
  • Fresnel lens - The faceted white dome that splits the PIR's view into segments so movement registers more strongly.
  • Potentiometer (pot) - An adjustable resistor; the HC-SR501 has two, for sensitivity and time delay.
  • Active buzzer - A buzzer with its own tone circuit; you only switch it on/off, so gpiozero's Buzzer object drives it.
  • Docstring - A short triple-quoted description placed just under a def to explain what a function does.

Chapter summary

  • Event-driven programming means writing callbacks — functions that run automatically when an event happens — instead of a fixed sequence of steps.
  • Register a callback by name with no parentheses: pir.when_motion = sound_alarm. Adding parentheses runs it immediately by mistake.
  • when_motion and when_no_motion fire on the rising and falling edges of motion; wait_for_motion() instead blocks until motion arrives.
  • The HC-SR501 PIR is powered from 5 V, but its OUT pin is already 3.3 V, so OUT connects directly to a GPIO with no voltage divider — unlike the HC-SR04 ultrasonic sensor, whose 5 V ECHO does need one.
  • The PIR needs a 30–60 s warm-up and has two pots (sensitivity and time delay) for tuning.
  • PIR modules are commonly salvaged from dead motion-sensor lights and alarms — but only ever open battery or low-voltage devices, never mains-powered ones.
  • Organising code into small named functions, then into an importable module (alarm_tools.py), keeps the main program short and reusable.
  • A global declaration is needed to reassign a module-level variable (like the event counter) from inside a function.
  • An armed boolean flag, checked at the top of the callback, lets the same alarm be switched on and off — the same gating pattern used throughout professional software.
