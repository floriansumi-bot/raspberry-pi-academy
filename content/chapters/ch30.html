You already met the friendly side of networking in the beginner lesson — connecting to Wi-Fi, finding your Pi's IP, opening an SSH session. This chapter goes deeper into what is actually happening underneath: how a single packet travels from an app, through the kernel, out the wire, and back to the right place; the modern toolset that has quietly replaced the commands half the internet still tells you to use; why DNS resolution almost never works the way people think it does; what SSH is really proving when it lets you in; and how containers get their own private networks out of nothing but the kernel. Your Pi 5 runs full Debian with a real Linux network stack, which makes it a wonderful little networking lab — you can run a tiny server on it and watch the connection from three angles at once, or hand-build the plumbing Docker uses, all on a board that costs less than a textbook. Take your time; this is one of those topics that feels like magic right up until it clicks, and then it feels obvious.

Careful: The firewall and network-namespace work near the end of this lesson can lock you out of a headless Pi. A single wrong nftables default-drop rule will cut your SSH session and leave you unable to reconnect. Do that work on your Pi with a keyboard and screen attached, or on a spare Pi, or at the very least with a known way back in — never blind over SSH on a Pi you can't physically reach. The risky firewall project at the end is flagged with a ⚠️.

The path of a packet

Everything in this lesson makes more sense once you can picture where a packet actually goes. When your program sends data, it does not talk to the network card directly — it writes into a socket, and the kernel takes over from there. Outbound, simplified:

app write()s to a socket
  → kernel copies the bytes into a socket buffer
  → transport layer: TCP segments / UDP datagrams, with source + dest PORTS
  → IP layer: routing decision (which interface? — via the ROUTING TABLE)
  → netfilter hooks: firewall / NAT (this is where nftables runs)
  → device driver → the NIC → the wire

Inbound runs the same path in reverse. The clever part is the last step: when a packet arrives, the kernel has to decide which of the hundreds of open sockets it belongs to. It does that by demultiplexing on the 4-tuple — (source IP:port, destination IP:port). That tuple is unique per connection, which is the whole reason a single web server listening on port 443 can serve thousands of clients at once: every connection is a different tuple, so the kernel never gets confused about which packet is whose.

In plain words: A socket is the kernel's idea of "one end of a network conversation" — a thing your program reads from and writes to as if it were a file. A port is just a number that lets one machine host many conversations at once, and the 4-tuple is the full return address that keeps them all straight.

The modern toolset (and the one you should stop using)

Here is a frustrating truth about Linux networking: most of the commands you will find in old blog posts and Stack Overflow answers are deprecated, and worse, they quietly show you an incomplete picture. Knowing the modern replacements is not pedantry — it is the difference between debugging the real state of your Pi and debugging a half-truth.

Myth vs reality: Myth — "Use ifconfig to see your interfaces and netstat to see your ports." Reality — ifconfig, netstat, route, and iptables are all deprecated, and ifconfig in particular doesn't even show all of an interface's addresses. The maintained, accurate tools are the iproute2 suite (ip, ss) and nftables (nft). They are already on your Pi. Use them.
Old (avoid)ModernFor
ifconfigip addr, ip linkinterfaces & addresses
routeip routethe routing table
netstatsssockets & listening ports (faster, more complete)
arpip neighthe ARP / neighbour table
iptablesnftables (nft)firewalling (one framework replacing iptables/ip6tables/arptables/ebtables)
 
ip -br addr                 # brief: each interface and its addresses
ip route                    # the routing table; `ip route get 8.8.8.8` shows the chosen route + iface
ss -tlnp                    # listening TCP sockets + the owning process (the netstat replacement)
ss -tan state established   # every established TCP connection
ip neigh                    # who's on my local segment (the ARP cache)

The key insight: ss -tlnp is the command you will run a thousand times. It answers the single most common networking question — "what is listening, on which port, owned by which process?" — instantly and completely. On your Pi, start any little server and ss -tlnp will show you exactly where it landed.

DNS resolution: it's nsswitch, not resolv.conf

This is the single most widespread misconception in all of Linux networking, so it is worth slowing down for. When a program resolves a name like example.com, it does not "do DNS" directly. It calls getaddrinfo(), and the first thing that function consults is the hosts: line in /etc/nsswitch.conf, which lists the sources to try, in order:

# /etc/nsswitch.conf
hosts: files mdns4_minimal [NOTFOUND=return] resolve [!UNAVAIL=return] dns
#      ← /etc/hosts     ← mDNS (.local)               ← systemd-resolved   ← classic DNS
  • files → /etc/hosts. This is checked first, which is precisely why a line in /etc/hosts can override whatever DNS would say.
  • mdns4_minimal → multicast DNS, the magic that lets raspberrypi.local resolve on your LAN with no DNS server at all.
  • Only the final dns backend reads /etc/resolv.conf for its list of nameservers.
  • On systemd-resolved systems, the resolve backend queries a local stub listening at 127.0.0.53, and /etc/resolv.conf is often just a symlink to a file that stub generates.
Note: The classic confusion — "I put the right nameserver in /etc/resolv.conf but resolution still does something weird" — is almost never resolv.conf's fault. It is usually nsswitch ordering, a stale /etc/hosts entry winning before DNS ever runs, or the systemd-resolved stub at 127.0.0.53 in the middle. Chase the order, not the file.
dig example.com A           # query one specific record type
dig +trace example.com      # walk the chain yourself: root → TLD → authoritative
resolvectl status           # what systemd-resolved is actually doing (per-link servers, DNSSEC)
getent hosts example.com    # resolve THE WAY APPS DO — through nsswitch, not just DNS

That last one is the tell: dig talks straight to a DNS server, but getent hosts goes through the exact same nsswitch path your applications use — so when dig and getent disagree, you have just proved the difference matters.

How SSH actually works

You SSH into your Pi all the time, but the part most people never picture is the asymmetry — there are two completely separate identity checks happening, in two directions. Four steps:

  1. TCP connect on port 22 (by default).
  2. Key exchange. Using something like ECDH, both sides derive a shared symmetric session key over the open, insecure channel — without ever transmitting that key. From this point on, all traffic is symmetrically encrypted.
  3. Host key verification. The server proves its identity using its host key, and your client checks that against ~/.ssh/known_hosts. The famous "authenticity of host can't be established" prompt is simply first contact — you have never seen this Pi's host key before. A changed-key warning later means either the Pi was rebuilt (reflashed SD card → new host key) or someone is impersonating it.
  4. Client authentication. Now you prove who you are. With public-key auth, the server holds your public key in ~/.ssh/authorized_keys and challenges you to prove you possess the matching private key — which never leaves your machine. Password auth is the weaker fallback.

The key insight: these are two independent proofs pointing in opposite directions. The host key authenticates the server to you; your keypair authenticates you to the server. Neither secret is ever sent across the wire. And everything fancy — local/remote/dynamic tunnels, ProxyJump, agent forwarding — all rides on top of that one already-established encrypted channel.

ssh-keygen -t ed25519 -C "you@host"     # a modern key (prefer ed25519 over RSA-2048)
ssh-copy-id pi@raspberrypi.local         # install your PUBLIC key into the Pi's authorized_keys
ssh -L 8080:localhost:3000 pi@raspberrypi  # LOCAL forward: your :8080 → the Pi's :3000
ssh -R 8080:localhost:3000 pi@public       # REMOTE forward: expose a NAT'd local service outward
ssh -D 1080 pi@raspberrypi                 # DYNAMIC: a SOCKS proxy tunnelled through the Pi
In plain words: An SSH tunnel quietly carries some other connection inside your encrypted SSH session. -L (local) makes a port on your laptop pop out on the far side — handy for reaching a database or a dev server running on your Pi as if it were local. -R (remote) does the reverse, exposing something on your side out through the server. -D (dynamic) turns the whole thing into a general-purpose SOCKS proxy.

Network namespaces & veth: container networking, the primitive

Here is the idea that makes container networking stop being mysterious. A network namespace is a private copy of the entire network stack: its own interfaces, its own routing table, its own firewall rules, its own port space. Two processes can both bind port 8080 with no conflict at all, as long as they live in different namespaces — because to the kernel they are on different networks entirely.

But an isolated namespace with only a loopback interface can't talk to anything. To connect it to the outside world, you use a veth pair — a virtual ethernet cable. It always comes as two linked ends: whatever goes in one end comes out the other. You put one end inside the namespace and leave the other on the host (usually plugged into a bridge), and now the two can pass packets. That is the entire trick.

sudo ip netns add ns1
sudo ip netns exec ns1 ip addr        # inside ns1: only loopback — a totally isolated stack
# create a veth pair, move one end into ns1, give both ends IPs, and the two can ping each other
nsenter -t <pid> -n ss -tlnp          # run ss INSIDE a running container's netns, from the host

This is the exact mechanism Docker and Podman use under the hood — when you run a container on your Pi, it gets a namespace and a veth pair stitched to a host bridge, and nothing more magical than that. You will assemble it by hand in the next chapter on containers, but the project below lets you wire two namespaces together today with zero containers involved.

Firewalling with nftables

nftables replaces the whole sprawling iptables family with one clean framework. The most useful pattern is a default-drop input policy: deny everything by default, then explicitly allow only what you need. Here is a minimal, safe host policy for a Pi:

# /etc/nftables.conf — default-drop input, but never lock yourself out
table inet filter {
  chain input {
    type filter hook input priority 0; policy drop;
    ct state established,related accept     # allow replies to connections WE started
    iif "lo" accept                          # always allow loopback
    tcp dport 22 accept                      # SSH — KEEP THIS or you lock yourself out of the Pi
    ip protocol icmp accept                  # allow ping
  }
}

Two ideas carry this whole config. First, default-drop: the policy drop line means anything not explicitly accepted is silently discarded — a deny-by-default posture that is the heart of a good firewall. Second, stateful filtering: the ct state established,related accept line uses the kernel's connection tracker so that replies to connections you initiated come back in automatically. Without it, a default-drop policy would block the responses to your own outbound requests, and basic things like apt update would hang.

Careful — the line that matters most: tcp dport 22 accept is what keeps your SSH session alive. If you load a default-drop ruleset on a headless Pi without an SSH-allow rule, your current session dies and you cannot reconnect — you are locked out of your own Pi. Always keep the SSH rule, test new rulesets with a keyboard and screen attached (or on a spare Pi), and have a way back in before you run nft -f. Friendlier front-ends like ufw and firewalld generate nftables rules underneath and make this a little harder to get wrong.

Try it on your Pi

  1. Run a server and watch it from every angle. On your Pi, launch python3 -m http.server 8000. In another session, while you curl localhost:8000 from the Pi, find the listening socket with ss -tlnp, map the port to the process with sudo lsof -i :8000, and watch the raw packets with sudo tcpdump -i lo port 8000. You are now seeing the same single connection from three layers at once — socket, process-and-file-descriptor, and wire.
  2. DNS resolution lab. Run dig +trace example.com and watch the name resolve from the root servers downward — root, then the TLD, then the authoritative server. Now add a line to /etc/hosts pointing some name at 127.0.0.1, and prove with getent hosts thatname that your /etc/hosts entry beats DNS — a hands-on demonstration of nsswitch ordering. Compare dig (pure DNS) against getent (the app path) and watch them disagree.
  3. SSH key auth + hardening. Generate an ed25519 key on your laptop, install it onto the Pi with ssh-copy-id, and confirm key login works before changing anything else. Then in the Pi's /etc/ssh/sshd_config set PasswordAuthentication no and PermitRootLogin no, restart sshd, and optionally add fail2ban. You have just turned off the weakest door while keeping your own key working.
  4. ⚠️ nftables host firewall. Write the default-drop ruleset above into /etc/nftables.conf, keeping the tcp dport 22 accept line. Load it with sudo nft -f /etc/nftables.conf, verify with sudo nft list ruleset, and confirm a new inbound port (try the python3 -m http.server 8000 from project 1) is now blocked from another machine while your SSH session survives. Do this with a keyboard and screen on the Pi, or on a spare Pi — a mistake here cuts SSH and there is no remote undo.

Key terms

  • socket - The kernel's endpoint of a network conversation that a program reads from and writes to; demultiplexed to the right connection by the 4-tuple of source/destination IP and port.
  • 4-tuple - The (src IP:port, dst IP:port) address that uniquely identifies a connection, letting one server port serve thousands of clients at once.
  • ss - The modern, faster replacement for netstat; ss -tlnp shows what is listening, on which port, owned by which process.
  • ip (iproute2) - The maintained replacement for the deprecated ifconfig/route/arp; manages interfaces, addresses, routes, and the neighbour table.
  • nsswitch.conf - The file whose hosts: line sets the order of name-resolution sources (files, mDNS, DNS); the real reason resolution behaves as it does — not resolv.conf.
  • resolv.conf - The file listing DNS nameservers, read only by the dns backend at the end of the nsswitch order; often a symlink to systemd-resolved's generated config.
  • SSH host key - The key with which the server proves its identity to your client (checked against ~/.ssh/known_hosts); one of SSH's two independent proofs.
  • public-key auth - How you prove your identity to the server: it holds your public key in authorized_keys and challenges you to prove you hold the matching private key, which never leaves your machine.
  • SSH tunnel - A connection carried inside the encrypted SSH session: -L local forward, -R remote forward, -D dynamic SOCKS proxy.
  • network namespace - A private copy of the whole network stack (interfaces, routes, firewall, port space); the isolation primitive containers are built on.
  • veth pair - A virtual ethernet "cable" of two linked ends used to connect a network namespace to the host; how containers reach the outside world.
  • nftables - The modern firewall framework replacing the iptables family; supports stateful, default-drop policies via the kernel's connection tracker (ct state).
