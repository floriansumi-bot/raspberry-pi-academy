You already know how to type commands into the terminal on your Pi. This lesson pulls back the curtain on what really happens in the split second after you press Enter — because the shell isn't just a command launcher, it's a full programming language that rewrites your line before any program ever runs. Once you see that hidden "rewrite" step, a whole class of confusing bash bugs turns into simple mechanics.

The key insight: before a single program starts, bash transforms your command line through a fixed, multi-stage expansion pipeline. Nearly every "weird shell bug" is really you not knowing what the shell did to your line before it handed it off. Learn the pipeline, and the magic becomes mechanics.

Careful: This lesson has you deliberately break things to learn how they work — including running rm on oddly named files. Do your experiments in a throwaway folder, and if you want to be extra safe, do the destructive parts on a spare microSD card you can re-flash, not the Pi you care about. Everything here runs on the full 64-bit Debian Linux your Pi 5 boots into, with the same bash you use every day.

The Expansion Pipeline Nobody Teaches You

When you press Enter, bash doesn't just run what you typed. It first rewrites the line through a series of steps, in this exact order, every single time:

brace expansion   {a,b}      → a b
tilde expansion   ~          → /home/you
parameter/var     $x ${x}    → the value
command subst     $(cmd)     → cmd's stdout
arithmetic        $((1+1))   → 2
WORD SPLITTING    on $IFS    → splits unquoted results into separate words
GLOBBING          * ? [..]   → expands to matching filenames
quote removal                → strips the quotes themselves

By the time your program actually starts, it just receives a finished list of strings (its argv). It has no idea you typed * or $x. The shell already resolved all of it and handed over the final words.

In plain words: Think of the shell as an editor that reads your sentence, swaps in all the placeholders, splits it into words, and only then calls the program — passing it the finished sentence. The program never sees your shorthand.

Open a terminal on your Pi and try this:

echo *

It prints the names of the files in your current folder. Why? Because the shell expanded * into that file list before echo ever ran. echo just dutifully printed the words it was handed.

The same thing happens with ls *.txt: ls never sees the *. The shell expands *.txt into the matching filenames and passes ls the final list. If nothing matches, bash (by default) hands over the literal string *.txt — which is why you sometimes see ls: cannot access '*.txt'. That error is the shell's doing, not ls's.

The key insight: globbing is done by the shell, for every command. rm *, git add *, cp * dir/ — the program always receives an already-expanded file list. The program is not "smart about wildcards." The shell is.

Word Splitting: The Number One Source of Real Bugs

Look back at the pipeline. After your variables are expanded, any unquoted result is split into separate words on $IFS (the "internal field separator," which by default is space, tab, and newline). Then each of those words is glob-expanded. This single behavior causes more broken scripts than anything else in shell.

file="my report.txt"
rm $file          # BUG: becomes  rm my report.txt  → two arguments
rm "$file"        # CORRECT: one argument, the actual filename
The unquoted line — bash expands $file to my report.txt, then splits on the space into two words. rm is told to delete a file called my and a file called report.txt — neither of which exists.
The quoted line — the double quotes suppress word splitting, so rm receives one argument: the real filename, space and all.

The rule you will never break again: quote your variables. Use "$var" and "$@" (not $*) essentially always. The only time you actually want splitting is a rare, deliberate case — and then you do it on purpose, with your eyes open.

This one habit eliminates a huge class of failures all at once: spaces in filenames, empty variables silently vanishing, and stray glob characters in your data getting expanded by surprise. There's even a free tool, ShellCheck, that exists largely to nag you about exactly this — run it on every script you write.

Two settings let you control what happens when a glob matches nothing:

shopt -s nullglob   # no match → expands to nothing (instead of the literal pattern)
shopt -s failglob   # no match → error out loudly

A single-quoted string can't contain a single quote at all. And "$var" is what you want about 95% of the time. When in doubt, reach for double quotes.

Subshells, Command Substitution and Here-Docs

These three tools come up constantly once you start writing real scripts on your Pi.

A subshell ( ... ) runs in a forked child process. Any variable changes or cd done inside it do not affect the parent. So (cd /tmp && do_stuff) leaves you in exactly the directory you started in — handy when you want to pop somewhere, do a job, and come back without thinking about it.

Command substitution $(cmd) runs cmd in a subshell, captures its standard output, strips trailing newlines, and (if you leave it unquoted) word-splits the result. Prefer $(...) over the older backtick form `cmd` — it nests cleanly and reads far better.

now=$(date +%H:%M)
echo "It is $now on your Pi"

A here-doc feeds a whole block of text into a command's standard input:

cat <<EOF          # expands $vars inside
Hello $USER
EOF

cat <<'EOF'        # quoted delimiter → NO expansion (literal)
Costs $100 and $PATH stays literal
EOF

cat <<-EOF         # the dash strips leading TABS (for indenting in scripts)
	indented in source, flush in output
EOF
Unquoted EOF — variables like $USER get expanded inside the block.
Quoted 'EOF' — nothing is expanded; $100 and $PATH stay literal. Perfect for writing out a config file that contains dollar signs.
The <<- dash — strips leading tab characters so you can indent the here-doc neatly inside a function or loop.

And a here-string feeds a command just one string: grep foo <<< "$line".

Exit Codes and the Defensive Script Header

Every command returns a whole number from 0 to 255. 0 means success; anything non-zero means some kind of failure. The special variable $? holds the last command's code. && runs the next command only on success; || runs it only on failure.

mkdir build && cd build       # cd only if mkdir worked
command -v jq || echo "jq not installed"

Here is the header worth putting at the top of every non-trivial script you write on your Pi:

#!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t'
set -e — exit on any unhandled non-zero command. (Caveats: it's ignored inside if/&&/|| conditions and has some historical surprises — treat it as a safety net, not a replacement for real error handling.)
set -u — error on unset variables. Catches typos like $flie instantly instead of silently using an empty value.
set -o pipefail — a pipeline's exit code becomes the last non-zero stage, not just the final command's. Without it, false | true "succeeds" and you silently miss the failure.
IFS=$'\n\t' — drops the space from the field separator, so word-splitting only happens on newlines and tabs. Much safer around filenames with spaces.

Builtins vs Externals: Why cd Can't Be a Program

When you type a command with no slash in it, bash searches $PATH from left to right and runs the first matching file it finds. But some commands don't live in a file at all — they run inside the shell process itself. These are called builtins.

The key insight: cd must be a builtin. A normal program runs in a child process, and a child can't change its parent's working directory. So if cd were an external program, it would change directory in the child, then the child would exit — and you'd be exactly where you started. For that reason cd, export, read, [, and pwd are builtins by necessity. A few commands exist as both a builtin and an external file (echo, test, printf, kill), with subtly different behavior.

type -a echo      # builtin, alias, function, or file? AND where
command -v ls     # what would actually run
hash -r           # clear bash's PATH cache (fixes "command not found" after moving a binary)
Myth vs reality: The myth is "use which to find a command." The reality is that which is an external program that knows nothing about builtins, shell functions, or aliases — so it lies about cd, your custom ll alias, and more. Use type -a instead. It's shell-aware and tells you the truth about what will actually run.

Login vs Interactive: Why PATH Works in the Terminal but Not in Cron

Two independent questions decide which startup files bash reads when it launches — and getting this wrong is behind one of the most common "it works for me but not in the script" head-scratchers.

  • Login shell (SSH into your Pi, a console login, or bash -l): reads /etc/profile, then the first of ~/.bash_profile, ~/.bash_login, or ~/.profile.
  • Interactive non-login (opening a new terminal tab on the Pi desktop): reads ~/.bashrc.
  • Non-interactive (a script, or a cron job): reads neither by default — only $BASH_ENV if that's set.

The key insight: "My alias / PATH / custom tool works in my terminal but the cron job can't find it" is almost always this. Cron runs non-interactive and non-login, with a bare-bones environment — none of your ~/.bashrc customizations exist there. The classic fix is to source ~/.bashrc from ~/.bash_profile, and to never assume your comfy interactive environment exists inside a script.

Try It on Your Pi

The best way to lock this in is to make the shell misbehave on purpose, in a safe folder, then fix it. Pick a couple of these.

  1. Break it on purpose (easiest — do this today). In a throwaway folder, create files literally named my file.txt, -rf, $HOME, and *.txt. Then write a loop that processes them and watch unquoted variables and globs detonate. Fix every case with proper quoting. Nothing teaches word-splitting like watching rm $file go wrong in a sandbox. Teaches: word splitting, globbing, and why you quote.
  2. A prompt that tells you things (easy). Build a custom PS1 in ~/.bashrc that shows your current git branch, the previous command's exit code (colored red on failure), and the working directory. The catch: you must capture $? first, before any other command clobbers it. Teaches: the shell environment, exit codes, prompt expansion.
  3. A dotfiles repo with an install script (intermediate). Put your .bashrc, .vimrc and friends in a git repo, and write an installer that symlinks them into $HOME. Running it twice must be safe (idempotent). Teaches: symlinks, idempotency, and quoting paths correctly.
  4. A CLI tool with real argument parsing (intermediate). Write a bash tool with -h/--help, short flags via getopts, and git-style subcommands dispatched by a case statement. Make it pass ShellCheck with zero warnings. Teaches: getopts, OPTARG/OPTIND, and the standard usage convention.

Key terms

  • Expansion pipeline — the fixed sequence of rewrites (brace, tilde, variable, command substitution, arithmetic, word splitting, globbing, quote removal) that bash applies to every command line before running it.
  • Globbing — the shell expanding wildcard patterns like *, ?, and [..] into matching filenames. Done by the shell, not by the program you're running.
  • Word splitting — bash breaking an unquoted expansion into separate words on $IFS (space, tab, newline by default). The top cause of scripts breaking on filenames with spaces.
  • IFS — the Internal Field Separator: the set of characters bash splits unquoted words on. Default is space, tab, and newline.
  • Quoting — wrapping text in single quotes (fully literal), double quotes (expand variables but no splitting), or backslash (escape one character) to control what the shell does to it.
  • Command substitution — $(cmd), which runs a command, captures its output, and substitutes it into the line. Preferred over backticks.
  • Subshell — a forked child shell created by ( ... ); changes to variables or directory inside it don't affect the parent.
  • Here-doc — <<EOF ... EOF, a way to feed a multi-line block of text into a command's standard input.
  • Exit code — the 0–255 number a command returns; 0 is success, non-zero is failure. Stored in $?.
  • Builtin — a command that runs inside the shell process itself (like cd, export, pwd) rather than as a separate program file.
  • pipefail — the set -o pipefail option that makes a pipeline report failure if any stage fails, not just the last one.
  • Login vs interactive shell — the two independent axes that determine which startup files bash reads; the reason a tool can work in your terminal but not in a cron job.
