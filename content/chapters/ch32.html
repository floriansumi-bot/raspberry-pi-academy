This is the last lesson of the Linux track, and it's a different kind of lesson. Up to now you've been learning how Linux works — the shell, processes, files, permissions, networking, systemd, containers. Now we close the loop: you're going to rebuild the tools you've been using so the models finally click into your bones, and then ship a real, always-on service on your Pi — hardened, behind nginx, with TLS and monitoring. Your Raspberry Pi 5 is the perfect target for all of this. It's a full Debian machine with systemd, it's yours to break, and unlike a throwaway cloud droplet it sits on your desk drawing two watts, ready to be a tiny always-on server. By the end you'll have built something you'd be happy to point a friend's browser at — and you'll understand every layer underneath it.

There's an idea worth saying out loud before we start: you don't truly understand a system until you've rebuilt a piece of it. Reading about fork and exec is fine. Writing a 200-line shell that actually forks and execs a command, and discovering for yourself why cd can't be a child process, is a different category of understanding. This lesson has two halves — build-your-own classics, then integration capstones — and you should pick the projects that excite you. Depth beats coverage. Go deep on two and you'll learn more than skimming all of them.

Rebuild to understand

Reimplementing a tool forces you to confront the model behind it. You can't hand-wave past the part you didn't really get, because the computer won't run hand-waving. Each project below maps directly back to lessons earlier in this track — so as you build, you're not learning something new so much as finishing something you already started.

In plain words: "Build your own X" isn't about producing a better cat — the real cat is fine. It's that the act of writing it drags the hidden assumptions into the open, where you have to make them concrete. The throwaway program is the byproduct; the understanding is the product.

Build-your-own classics

Here are five classic projects, smallest first, each anchored to the earlier lessons it draws on. Start with the easy confidence-builders and work up to the keystone projects — the tiny shell and the PID-1 init — that reorganise how you think about the whole system.

1. Clone the simple ones: cat, wc, head

Write cat, wc, and head in C or Python. They look trivial and they almost are — but you'll wrestle with the genuinely fiddly bits every real Unix tool handles: parsing arguments, reading from either standard input or file arguments (the classic "read from a pipe when given no filename" behaviour), buffered I/O, and counting lines versus words versus bytes correctly. Small, fast, satisfying wins to warm up on.

Draws on: the shell and standard streams (stdin/stdout/stderr), redirection and pipes.

2. A tiny shell — the keystone project

This is the one that changes how you see everything. Write a REPL — read a line, tokenise it, then fork() a child, have the child execvp() the command, and have the parent waitpid() for it to finish. That loop is a shell. Then add a couple of builtins, cd and exit, and you'll hit the lesson that no amount of reading teaches as well as one bug does:

The key insight: cd must be a builtin — it has to run in the shell process itself, not in a forked child. If you try to make cd an external command, it forks a child, the child changes its own directory, and the child exits. The parent shell never moved. Watching your own shell "fail" to change directory until you make cd a builtin teaches the fork/exec/wait model permanently.

Once the basic shell works, add pipes with pipe() and dup2() — wiring one command's stdout to the next command's stdin is exactly the redirection model you learned, now seen from the producing side.

Draws on: the shell, processes (fork/exec/wait), redirection and pipes. A wonderful guide is Stephen Brennan's ~200-line C shell — read it, type it, then extend it.

3. An HTTP server from raw sockets

Frameworks hide what HTTP actually is. Strip the magic away. Start with this one-liner to watch the raw wire format with your own eyes:

while true; do printf 'HTTP/1.1 200 OK\r\n\r\nhello' | nc -l 8080; done

Point a browser at http://your-pi:8080 and you'll see hello — you just served HTTP with a shell loop and nc. Now write the real thing: socket() → bind() → listen() → accept() → recv()/send(), and parse the request line (GET /path HTTP/1.1) yourself. After this, "a web server" stops being a black box and becomes a program you could have written — because you did.

Draws on: networking and sockets, the shell.

4. A simple init / PID 1 — the capstone of the process model

Inside a container, run a process as PID 1: launch a child, forward signals to it (so docker stop actually reaches your app), and reap zombie processes by calling wait() in a loop. When this works, you'll understand in your bones why containers need a tiny init like tini, and why PID 1 is special.

In plain words: when a process exits, it leaves behind a little "zombie" entry in the process table until its parent collects the exit status with wait(). Normally init adopts and reaps orphans automatically. But the kernel gives PID 1 no special help here — if your program is PID 1 and never calls wait(), zombies pile up forever. That's why a bare app run as PID 1 in a container needs a real init in front of it.

Draws on: processes and signals, containers. Compare your result to dumb-init and tini — the real-world ~200-line versions of exactly what you wrote.

5. grep and ls clones

grep is line filtering: read lines, test each against a substring or a regex, print the matches. ls is more revealing than it looks — readdir() to walk the directory, stat() each entry, then format the mode field yourself, turning the permission bits back into the rwxr-xr-x string you've read a thousand times. Building ls means producing the permissions display from the other side of everything you learned about permissions.

Draws on: the shell, the filesystem, permissions.

Tip: Want graded specs instead of going freestyle? codingchallenges.fyi has staged, language-agnostic specs for cat/wc/grep/cut/shell, and CodeCrafters gives you a real test suite for build-your-own shell/git/http-server/redis. Both turn "build a thing" into "pass these checks", which makes progress concrete and keeps you honest.

A modern CLI toolbox

Before the capstones, a gift for daily life. There's a whole generation of command-line tools — mostly rewritten in Rust or Go — that are faster, have saner defaults, are .gitignore-aware, and are genuinely nicer to live in. None are required; the standard tools this track taught are what's on every server you'll ever SSH into, and you should keep them in muscle memory. But adopting a handful of these will compound across everything you do.

Tool Replaces Why it's nicer
ripgrep (rg) grep -r Skips .gitignored files and binaries by default, multithreaded, much faster: rg -i TODO --type py.
fd find Sane syntax (fd '\.py$' vs find . -name '*.py'), parallel, .gitignore-aware, coloured.
fzf — (new power) Interactive fuzzy finder. Bind it to Ctrl-R for fuzzy shell history; pipe anything into it: vim $(fzf). The single highest-ROI install.
jq — (new power) A query/transform language for JSON. Indispensable for APIs: curl … | jq '.items[] | {name,id}'. JSON is everywhere; learn it.
bat cat Syntax highlighting, line numbers, a git change gutter, and automatic paging.
eza ls Colours, icons, git status, and a built-in --tree view.
tmux — (new power) Persistent terminal sessions that survive disconnection — reattach after your SSH drops mid-task — plus split panes and multiple windows.
zoxide cd Jump to frequent directories by "frecency": z proj instead of cd ~/code/work/project.

Two of these earn special mention because you'll use them constantly on the Pi. tmux is the one "old" tool in the list and it's essential for remote work: start a named session, do your thing, and when your SSH connection drops mid-upgrade your shells keep running — reattach and they're exactly where you left them.

tmux new -s work      # start a named session
# Ctrl-b "  split horizontally   Ctrl-b %  split vertically   Ctrl-b d  detach
tmux attach -t work   # reattach later — your shells kept running the whole time

And jq turns the wall of JSON every modern API returns into something you can actually slice:

curl -s https://api.github.com/repos/torvalds/linux | jq '{name, stars: .stargazers_count}'
rg --json TODO | jq -r 'select(.type=="match") | .data.path.text'
Tip: Don't alias ls=eza and cat=bat on day one — you'll get tangled up the moment you SSH into a plain server that doesn't have them. Learn the standard tools first (this track did that deliberately), then add the modern ones as personal quality-of-life. If you adopt only three, make them fzf, ripgrep, and jq.

Capstones — build something real on your Pi

Now the payoff. These four capstones combine multiple lessons into the real-world shape you'd actually deploy. The cloud world does this on a throwaway droplet with a public IP — but your Pi is the droplet. It's an always-on Linux box you control completely, which makes it the ideal place to make these mistakes safely and learn from them. Do them in order; each builds on the last. Use a spare microSD card so you can wipe and start over fearlessly.

  1. Harden your Pi into a proper little server. Starting from a fresh Raspberry Pi OS install, build a secure baseline: create a non-root sudo user and stop logging in as the default account; switch SSH to key-only authentication (set PasswordAuthentication no and PermitRootLogin no in sshd_config) so passwords can't be brute-forced; put up an nftables default-drop firewall that allows only SSH and your app's ports and denies everything else by default; and enable unattended-upgrades so security patches install themselves. Test that you can still log in from a second terminal before you close your working session — locking yourself out is the classic first mistake, and a default-drop firewall is exactly how it happens. Pulls together: users & permissions, networking & firewalls, SSH.
  2. Deploy an app behind nginx with a hardened systemd service and TLS. Run your app — any language, or the HTTP server you built in the first half — as a hardened systemd service bound to localhost, using the lockdown directives DynamicUser=yes, ProtectSystem=strict, and NoNewPrivileges=true (and AmbientCapabilities=CAP_NET_BIND_SERVICE only if it truly needs a low port). Put nginx in front as a reverse proxy, forwarding public requests to your app on localhost. If you have a domain pointed at your Pi, add Let's Encrypt TLS with certbot for real HTTPS. Confirm graceful restarts with systemctl reload nginx and that your app's logs land in journalctl -u yourapp. This is the standard production deployment shape — and now you've built it from primitives you understand. Pulls together: systemd, permissions & capabilities, networking.
  3. Add real monitoring. Install node_exporter (which exposes your Pi's CPU, memory, disk, and temperature as metrics), Prometheus (which scrapes and stores those metrics over time), and Grafana (which graphs them) — each as its own systemd unit. Import a host dashboard and wire one alert, such as "disk over 85% full". Pulls together: the observability mindset, systemd, networking.
  4. Tie it all together in one reproducible bootstrap script. Fold capstones 1–3 into a single idempotent bootstrap script (a shell script, or an Ansible playbook if you want to go further): a freshly flashed Pi becomes a hardened host running a TLS-terminated, monitored app under systemd — from zero, repeatably. The real test: if you can reflash the card, run one command, and get the exact same working server back, you've operationalised the entire track. That's not a toy — that's the muscle real infrastructure engineering is built on. Pulls together: everything.
Careful: Prometheus and Grafana have no built-in authentication on their raw metrics endpoints. Bind node_exporter and Prometheus to localhost only — never expose them to the open internet — and reach Grafana through nginx with a login, or over an SSH tunnel. An open Prometheus is a free map of your machine for anyone who finds it.
Note: Because your Pi sits on your home network, capstone 2's Let's Encrypt step needs a domain name and a way for the certificate challenge to reach your Pi (a port-forward on your router, or a DNS challenge). If that's more than you want to set up today, do everything else and use a self-signed certificate or plain HTTP on your LAN — the systemd-and-nginx shape is the lesson; public TLS is the optional flourish.

The key insight: none of these capstones introduces a genuinely new concept. Every piece — the non-root user, the firewall, the hardened service, the reverse proxy, the metrics — is something you already met. The capstone is learning to compose them into a system that stays up, stays patched, and stays observable. That composition is systems engineering, and you can now do it on hardware that fits in your palm.

Key terms

  • fork / exec / wait - The trio at the heart of the shell: fork() makes a child process, the child exec()s the command, and the parent wait()s for it. Building a shell makes this concrete — and shows why cd must be a builtin.
  • builtin - A command the shell runs in its own process rather than forking a child for, because it must change the shell's own state — the textbook case being cd.
  • PID 1 / init - The first process in a system or container; it must forward signals to its children and reap zombies with wait(), which is why containers use a tiny init like tini.
  • zombie / reaping - A finished process whose exit status no parent has collected yet; the parent "reaps" it by calling wait(). A PID-1 that never reaps lets zombies accumulate.
  • reverse proxy - A server (here nginx) that sits in front of your app, receives public requests, and forwards them to the app on localhost — adding TLS, logging, and a single front door.
  • Let's Encrypt - A free, automated certificate authority; with certbot it issues and renews real HTTPS certificates for a domain, so your Pi can serve genuine TLS.
  • node_exporter - A small service that exposes a host's metrics (CPU, memory, disk, temperature) for Prometheus to scrape; the standard way to monitor a Linux machine.
  • default-drop firewall - A firewall policy (e.g. with nftables) that blocks all traffic by default and allows only explicitly permitted ports — the safe baseline for an internet-facing host.
  • ripgrep (rg) - A fast, modern grep replacement that skips .gitignored files and binaries by default and searches in parallel.
  • fzf - An interactive fuzzy finder you pipe lists into; bound to Ctrl-R it turns shell-history search into instant fuzzy matching.
  • jq - A query and transform language for JSON, indispensable for slicing the output of modern APIs from the command line.
  • tmux - A terminal multiplexer whose sessions survive disconnection, so remote work keeps running when your SSH connection drops; also splits panes and windows.
