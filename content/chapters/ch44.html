Across the last few chapters you have salvaged a pile of dead electronics: a LEGO NXT's geared motors and encoders, a drawer phone that became a wireless camera, an ultrasonic distance sensor, a web dashboard you can open from your sofa. In this grand finale you stop building parts and start building one robot. It will roll on NXT legs, see through a phone's eye, think with the Pi's brain, watch ahead with an ultrasonic whisker, and obey you from a web remote in your hand — nearly all of it rescued from the e-waste pile. Along the way you will learn the Python that ties salvaged hardware into a single program: modules and imports, a simple state machine, the main control loop, and OpenCV colour tracking that turns a camera image into a steering decision.

What You'll Build & Learn

This is the Maker Lab capstone: the lesson where every loose end ties together. You will not re-learn how to wire an H-bridge or a voltage divider — you built those already. Instead you will write the software glue that makes four salvaged subsystems behave as one machine: the Junkbox AI Rover.

The finished rover has three personalities, switched from your phone: it can be driven by hand (manual), it can chase a coloured target on its own (follow), and it can wander while dodging walls (avoid). One small Python program holds all three, and a coloured marker, a web browser, or an obstacle decides what it does next.

Python fundamentals (named)

  • Modules & imports — you will take the Robot class you wrote in Lesson 42, save it as its own file robot.py, and import it into every program here. Writing the hard part once and reusing it everywhere is exactly what a module is for.
  • A simple state machine — a single variable (held in a small dictionary) remembers which mode the rover is in, and the program behaves differently in each. This is how real robots, games and appliances organise "what should I be doing right now?".
  • The main control loop — the while True: heartbeat that reads the world, decides, and acts, several times a second, forever.
  • OpenCV colour tracking — convert a camera frame to HSV, threshold a colour, find the biggest blob, and read its centre. It reinforces classes (Lesson 42) and Flask (Lesson 41).

Electronics fundamentals (named)

  • System integration — the power architecture that lets it all coexist: a separate ~9 V motor battery, the Pi on its own supply, and one common ground tying them together. This is the single rule that makes or breaks a robot.
  • Reusing the ultrasonic sensor — the HC-SR04 from Lesson 38, still through its 5 V→3.3 V divider, now used as a collision whisker that can override the brain.
  • A wiring recap, not a re-teach — we link back to Lessons 38 and 42 for the full diagrams and only summarise the connections here.

AI / vision fundamentals (named)

  • The phone as eyes — the IP-webcam trick from Lesson 43: the phone streams its camera over Wi-Fi and the Pi reads it with OpenCV. We turn the picture into a single steering number, and we are honest about frame rate and latency on a Pi 5.
Note: You do not need every part to learn from this chapter. If you have no NXT motors, any cheap DC gear-motor pair works; if you have no phone to spare, the colour-tracking code still runs on a Pi Camera. We always say "your robot" rather than assume a particular kit. Where hardware is missing, the code and the ideas still teach you everything.

In plain words: a common ground is a single 0 V wire that every board shares. The Pi's 3.3 V "HIGH" only means anything to the driver if both agree on where 0 V is. Two batteries with no shared ground are like two people measuring height from different floors — their numbers cannot be compared.
Careful — the power rules that protect your Pi:
  • Wheels off the ground for the first tests. Prop the chassis on a mug or box so the wheels spin freely in the air. A bug in a follow loop can otherwise drive the rover off a table.
  • Separate motor battery. Motors run from their own ~9 V pack at the driver's VM — never from the Pi's 5 V pin. The Pi cannot spare the amps, and motor noise can crash it.
  • Common ground. Join the battery −, the driver GND, the sensor GND and the Pi GND at one rail.
  • Never feed motor voltage into the Pi. The motors' white/black power wires touch only the driver outputs, never a GPIO or power pin. A 9 V spike or a stalled motor's current would destroy the SoC.
  • Level-shift the ECHO line. The HC-SR04's ECHO outputs 5 V; it reaches GPIO 24 only through its 330 Ω/470 Ω divider.
  • Power off to rewire. Shut down and unplug the Pi before changing wiring; re-power only after a full check.

Step 1 — The Drive Base as a Module

The first job is to make Lesson 42's Robot class reusable from any program. The trick is the simplest, most useful idea in Python: put it in its own file (a module) and import it.

In plain words: a module is just a Python file you import into another. When you write from robot import Robot, Python finds robot.py beside your program and hands you the Robot class from inside it. You write the messy motor code once; every other file gets it for free.

If you still have robot.py from Lesson 42, you are done — reuse it unchanged. If not, save exactly this as robot.py in your project folder. It is the same class you built before.

# robot.py  --  the drive base from Lesson 42, as an importable module
from gpiozero import Motor


class Robot:
    """Two salvaged motors wired to a DRV8833, wrapped as one robot."""

    def __init__(self, left_pins, right_pins, speed=0.6):
        self.left = Motor(forward=left_pins[0], backward=left_pins[1])
        self.right = Motor(forward=right_pins[0], backward=right_pins[1])
        self.speed = speed

    def forward(self, speed=None):
        s = speed if speed is not None else self.speed
        self.left.forward(s)
        self.right.forward(s)

    def backward(self, speed=None):
        s = speed if speed is not None else self.speed
        self.left.backward(s)
        self.right.backward(s)

    def turn_left(self, speed=None):
        s = speed if speed is not None else self.speed
        self.left.backward(s)
        self.right.forward(s)

    def turn_right(self, speed=None):
        s = speed if speed is not None else self.speed
        self.left.forward(s)
        self.right.backward(s)

    def stop(self):
        self.left.stop()
        self.right.stop()

Line 2 — from gpiozero import Motor: Brings in the ready-made Motor object that drives one two-input H-bridge channel with PWM speed control.

Line 5 — class Robot:: Begins our own blueprint. The triple-quoted line is a docstring describing it; everything indented below belongs to the class.

Line 8 — def __init__(self, left_pins, right_pins, speed=0.6):: The initialiser, run automatically when you build a Robot. It takes a pin pair for each side, like (20, 21), plus a default speed.

Lines 9–10 — self.left = Motor(...) / self.right = Motor(...): Build one Motor per side and store them on this robot. left_pins[0] is the forward pin, left_pins[1] the backward pin.

Line 11 — self.speed = speed: Remembers the default speed so the methods can fall back to it.

Lines 13–16 — forward: The one-line if picks the speed (the one you passed, or the stored default), then drives both wheels forward so the robot rolls straight.

Lines 18–21 — backward: The mirror image — both wheels reverse.

Lines 23–26 — turn_left: Spins on the spot to the left by running the left wheel backward and the right wheel forward.

Lines 28–31 — turn_right: The opposite — left forward, right backward.

Lines 33–35 — stop: Stops both motors. We will call this whenever anything ends, so the robot never runs off.

Now a tiny program that uses the module to prove the drive base. Save it as test_drive.py in the same folder, with the wheels propped up.

# test_drive.py  --  a quick shake-down using the imported module
from robot import Robot
from time import sleep

robot = Robot(left_pins=(20, 21), right_pins=(19, 26))

print("Forward...")
robot.forward(0.5)
sleep(1.5)

print("Turn right...")

sleep(1.5)

Line 2 — from robot import Robot: The whole point of Step 1. Python loads robot.py and gives us the Robot class. This program never mentions a single GPIO pin's wiring — the module hides it.

Line 5 — robot = Robot(left_pins=(20, 21), right_pins=(19, 26)): Builds one robot with our pin choices from the recap table. Naming the arguments keeps the two sides from getting muddled.

Lines 7–9 — forward: Drive both wheels forward at half speed for 1.5 seconds. Half speed is gentle enough to watch.

Lines 11–13 — turn: Spin right for 0.7 seconds, then check the wheels turn the way you expect.

Lines 15–19 — finish: Drive forward again, then stop(). Always end a robot program with a stop so the motors cannot keep running.

Note: If a wheel spins the wrong way, you have two easy fixes (both from Lesson 42): swap that motor's white and black wires at the driver output, or swap its forward= and backward= pins where you build the Robot. Pick one.
Tip: Keep every file of this project in one folder. Python's import looks for robot.py beside the program that imports it, so a stray file in another folder will give a confusing ModuleNotFoundError: No module named 'robot'.

Step 2 — Give It Eyes

Now the camera. In Lesson 43 you turned an old phone into a Wi-Fi camera by running an IP-webcam app (IP Webcam, DroidCam or Iriun) and reading its stream with OpenCV. We reuse that exactly — the phone is the rover's eye, mounted facing forward on the chassis.

OpenCV is not preinstalled on Bookworm, and the PEP 668 rule blocks a plain pip install. Install it inside a virtual environment, the same habit as Flask in Lesson 41:

python3 -m venv ~/rover
source ~/rover/bin/activate
pip install opencv-python flask

Line 1 — python3 -m venv ~/rover: Creates a private Python environment in a folder called rover in your home folder, isolated from the system Python.

Line 2 — source ~/rover/bin/activate: Switches your terminal into it; the prompt gains a (rover) prefix. Now pip installs here, not into the protected system Python.

Line 3 — pip install opencv-python flask: Installs both libraries we need for the rover at once — OpenCV for vision and Flask for the web remote — with no PEP 668 error. (As a system-wide alternative, sudo apt install python3-opencv python3-flask also works.)

Careful: gpiozero lives in the system Python, not your venv. So either create the venv with python3 -m venv --system-site-packages ~/rover so it can still see gpiozero, or install it into the venv with pip install gpiozero lgpio. Without one of these, from gpiozero import Motor will fail with ModuleNotFoundError once the venv is active.

Here is a robust frame-grabber. It opens the phone stream once, then loops, and — crucially for a moving robot — it survives dropped frames instead of crashing. Save it as eyes_test.py.

# eyes_test.py  --  read the phone's Wi-Fi camera with OpenCV
import cv2

PHONE_URL = "http://PHONE-IP:8080/video"   # the address the app shows
cap = cv2.VideoCapture(PHONE_URL)

if not cap.isOpened():
    print("Could not open the stream. Is the phone app running?")
    raise SystemExit

print("Streaming. Press q in the window to quit.")
while True:
    ret, frame = cap.read()
    if not ret:
        print("Dropped a frame - retrying...")
        continue                # don't crash; just try the next frame
    cv2.imshow("Rover eyes", frame)
    if cv2.waitKey(1) & 0xFF == ord("q"):
        break

cap.release()
cv2.destroyAllWindows()

Line 2 — import cv2: Imports OpenCV. The module is called cv2 for historical reasons; it does all the heavy video and image work.

Line 4 — PHONE_URL = "http://PHONE-IP:8080/video": The phone's MJPEG stream. Replace PHONE-IP with the address the app displays (for example 192.168.1.42); the IP Webcam app serves video at the /video path on port 8080.

Line 5 — cap = cv2.VideoCapture(PHONE_URL): Opens the stream. Passing an HTTP URL instead of a camera number is all it takes — OpenCV reads the MJPEG frames as if they were a video file.

Lines 7–9 — if not cap.isOpened(): Checks the stream actually opened. If the app is not running or the IP is wrong, we say so clearly and exit rather than loop on nothing.

Line 13 — ret, frame = cap.read(): Grabs the next frame. ret is True/False (did a frame arrive?) and frame is the image, a grid of pixels.

Lines 14–16 — if not ret: ... continue: The robust bit. Wi-Fi cameras drop the odd frame; rather than break out and stop, we print a note and continue to the next loop pass. A rover whose eyes blink should not fall over.

Line 17 — cv2.imshow("Rover eyes", frame): Shows the frame in a window so you can confirm the camera is aimed correctly. On a headless rover you would skip this.

Line 18 — cv2.waitKey(1) & 0xFF == ord("q"): Waits 1 ms for a key; pressing q breaks the loop. The wait also lets the window redraw.

Lines 21–22 — tidy up: Release the stream and close the window. Always release the capture when you finish.

Be honest about speed. Reading an MJPEG stream over Wi-Fi and decoding each frame costs time. On a Pi 5 expect roughly 10–20 frames per second at 640×480, with a little latency — the picture you act on is a fraction of a second old. That is plenty for a gentle follower, but it is why we keep drive speeds low so the rover does not overshoot between decisions.
Careful: Android often stops the camera when the screen locks or the app is backgrounded, and usually only one program can read the stream at a time. Keep the app in the foreground with the screen awake (ideally on charge), and remember the phone and Pi must be on the same Wi-Fi network.

Step 3 — See a Target (Colour Tracking)

A frame is just a grid of colours. To follow something we need one number: where, left to right, is our target? The simplest, most beginner-friendly way to get it is colour tracking — pick a bright marker (a ball, a sticky note, a painted lid), and find the biggest patch of that colour in the frame.

In plain words: HSV (Hue, Saturation, Value) is a way of describing colour that splits "what colour" (hue) from "how bright" (value). It is far easier to threshold than the usual red/green/blue, because a single hue range catches a colour across shadows and highlights. OpenCV converts to it in one call.

The pipeline has four steps: convert the frame to HSV, make a black-and-white mask of just our colour, find the largest blob (contour) in that mask, and compute its centre and size.

Save this as vision.py. It is a module too: it exposes one function, find_target(frame), that the control loop and the web server will both call.

# vision.py  --  find a coloured target in a frame, return its centre and size
import cv2
import numpy as np

# HSV range for a bright GREEN marker. Tune these for your colour/lighting.
LOWER = np.array([40, 80, 80])
UPPER = np.array([85, 255, 255])
MIN_AREA = 500          # ignore blobs smaller than this (noise)


def find_target(frame):
    """Return (cx, area) of the largest matching blob, or (None, 0)."""
    hsv = cv2.cvtColor(frame, cv2.COLOR_BGR2HSV)
    mask = cv2.inRange(hsv, LOWER, UPPER)

    contours, _ = cv2.findContours(
        mask, cv2.RETR_EXTERNAL, cv2.CHAIN_APPROX_SIMPLE)
    if not contours:
        return None, 0

    biggest = max(contours, key=cv2.contourArea)
    area = cv2.contourArea(biggest)
    if area < MIN_AREA:
        return None, 0

    M = cv2.moments(biggest)
    cx = int(M["m10"] / M["m00"])
    return cx, area

Lines 2–3 — imports: OpenCV for the vision, and numpy (imported as np) for the colour-bound arrays OpenCV expects.

Lines 6–7 — LOWER / UPPER: The HSV range that counts as "our colour". These values catch bright green; the three numbers are hue, saturation and value. You will tune them for your marker and room (see the tip below).

Line 8 — MIN_AREA = 500: A noise floor. Stray speckles of the right colour make tiny blobs; ignoring anything smaller than 500 pixels stops the rover chasing dust.

Line 13 — hsv = cv2.cvtColor(frame, cv2.COLOR_BGR2HSV): Converts the frame from OpenCV's default BGR to HSV, the colour space that is easy to threshold.

Line 14 — mask = cv2.inRange(hsv, LOWER, UPPER): Builds the black-and-white mask: every pixel inside the colour range becomes white (255), everything else black (0).

Lines 16–17 — cv2.findContours(...): Traces the outlines of the white regions. RETR_EXTERNAL keeps only outer outlines (we do not care about holes); CHAIN_APPROX_SIMPLE stores each outline compactly. It returns a list of contours.

Lines 18–19 — nothing found: If the list is empty, the colour is not in view, so return (None, 0) to mean "no target".

Line 21 — biggest = max(contours, key=cv2.contourArea): Picks the largest blob by area — almost always our marker rather than a stray fleck.

Lines 22–24 — area gate: Measure the blob's area; if it is below MIN_AREA it is noise, so again return "no target".

Line 26 — M = cv2.moments(biggest): Computes the blob's moments — weighted pixel sums that describe its shape. m00 is its area; m10 is the sum of x-positions.

Line 27 — cx = int(M["m10"] / M["m00"]): Divides those to get the horizontal centre of mass — the centroid's x in pixels. This single number is what we steer by.

Line 28 — return cx, area: Hand back the centre and the size. The control loop uses cx for steering left/right and area for how close the target is (a bigger blob is nearer).

Tip — tuning the colour: Hues in OpenCV run 0–179 (not 0–359). Rough starting hues: red wraps around 0/179, green ≈ 40–85, blue ≈ 100–130. The quickest way to tune is to print the HSV value at the centre of your marker (print(hsv[120, 160]) on a 320×240 frame) and set LOWER/UPPER a little either side of it. Bright, saturated colours track far more reliably than pale ones.
The upgrade path. Colour tracking is wonderfully simple but it only knows "that colour", not "that thing". To follow a person or a specific object regardless of colour, swap find_target for the TensorFlow Lite or IMX500 object detection you met in Lessons 19 and 42: it returns labelled boxes, and you steer by a box's centre exactly the same way. The control loop below does not change — only the function that produces cx does. That is the payoff of hiding vision behind one tidy function.

Step 4 — The Follow Behaviour and the State Machine

Now we make the rover act. The follow behaviour is a tiny piece of logic: turn toward the target if it is off to one side, drive forward if it is centred, and stop if there is no target. We map the centroid's horizontal offset to a turn, and the blob's area to forward/back.

But a good rover is not only a follower. We want to switch between driving it by hand, letting it chase the marker, and letting it wander while dodging walls. That is a job for a state machine.

In plain words: a state machine is a program that is always in exactly one state (here: manual, follow, or avoid) and behaves differently in each. An event — a button press, a too-close wall — can move it to another state. Holding the current state in one variable keeps "what should I be doing?" in a single, easy-to-read place.

Here is the brain. Save it as brain.py. It imports the drive base and the vision module, adds the ultrasonic, holds the current mode in a dictionary, and runs the main control loop. The Flask remote (next step) will flip STATE["mode"] from your phone.

# brain.py  --  the main control loop and state machine
import cv2
from gpiozero import DistanceSensor
from robot import Robot
from vision import find_target

robot = Robot(left_pins=(20, 21), right_pins=(19, 26))
# ECHO via a 330 Ohm / 470 Ohm divider; TRIG direct (Lesson 38)
sonar = DistanceSensor(echo=24, trigger=23, max_distance=2)

PHONE_URL = "http://PHONE-IP:8080/video"
cap = cv2.VideoCapture(PHONE_URL)

FRAME_W = 320
CENTRE_X = FRAME_W // 2
DEAD_ZONE = 40          # pixels either side of centre we call "centred"
NEAR_AREA = 20000       # blob this big means the target is close enough
STOP_CM = 20            # stop if anything is closer than this

# The whole state of the rover lives in one dictionary.
STATE = {"mode": "manual"}


def too_close():
    """True if the ultrasonic sees an obstacle within STOP_CM."""
    return sonar.distance * 100 < STOP_CM


def do_follow(frame):
    """Steer toward the coloured target, or wait if none is seen."""
    small = cv2.resize(frame, (FRAME_W, 240))
    cx, area = find_target(small)
    if cx is None:
        robot.stop()                 # nothing to follow - wait
        return
    offset = cx - CENTRE_X
    if offset < -DEAD_ZONE:
        robot.turn_left(0.4)         # target is to the left
    elif offset > DEAD_ZONE:
        robot.turn_right(0.4)        # target is to the right
    elif area < NEAR_AREA:
        robot.forward(0.4)           # centred but far - approach
    else:
        robot.stop()                 # centred and close enough


def do_avoid():
    """Wander forward, turning away when a wall gets close."""
    if too_close():
        robot.turn_right(0.5)        # spin away from the obstacle
    else:
        robot.forward(0.4)


print("Rover running. Ctrl+C to stop.")
try:
    while True:
        # SAFETY REFLEX: in any mode, a close wall stops the wheels first.
        if STATE["mode"] != "manual" and too_close():
            robot.stop()

        if STATE["mode"] == "follow":
            ret, frame = cap.read()
            if ret and not too_close():
                do_follow(frame)
        elif STATE["mode"] == "avoid":
            do_avoid()
        # in "manual" the loop does nothing; the web routes drive directly
except KeyboardInterrupt:
    robot.stop()
    print("\nStopped.")

Lines 2–5 — imports: OpenCV for frames, gpiozero's DistanceSensor for the ultrasonic, and our own two modules — Robot from robot.py and find_target from vision.py. The whole rover is assembled from imports.

Line 7 — robot = Robot(...): Builds the drive base on the recap-table pins.

Line 9 — sonar = DistanceSensor(echo=24, trigger=23, max_distance=2): The HC-SR04 from Lesson 38, ECHO still through its divider. max_distance=2 lets it report up to two metres; .distance returns metres.

Lines 11–12 — the camera: Open the phone stream once, before the loop, so we are not re-opening it every pass.

Lines 14–18 — the tuning numbers: The frame width and its middle column; a DEAD_ZONE tolerance so the rover does not twitch when the target is roughly centred; NEAR_AREA, the blob size that means "close enough, stop approaching"; and STOP_CM, the collision distance.

Line 21 — STATE = {"mode": "manual"}: The state machine in one line. A dictionary holds the current mode; everything else reads it. Starting in manual means the rover never bolts the instant it powers on.

Lines 24–26 — too_close(): A small helper that turns the ultrasonic's metres into centimetres and answers a yes/no: is anything within STOP_CM? Naming it makes the loop read like English.

Lines 29–33 — resize and detect: Shrink the frame to a fixed 320×240 (smaller frames are faster and keep CENTRE_X consistent), then ask find_target for the marker's centre and size.

Lines 34–36 — no target: If find_target returned None, stop and wait. A follower that charges off when it loses sight of its target is a runaway.

Line 37 — offset = cx - CENTRE_X: How far left (negative) or right (positive) of centre the target is — the whole steering decision in one number.

Lines 38–45 — the follow logic: Well to the left → turn left; well to the right → turn right; centred but the blob is still small (far away) → drive forward; centred and the blob is big (close) → stop. Steering to push offset toward zero keeps the target in front.

Lines 48–53 — do_avoid(): The wander behaviour. If the whisker sees a wall, spin away; otherwise roll gently forward. Crude but effective — the same idea as a robot vacuum.

Line 58 — while True:: The main control loop — the rover's heartbeat. Each pass reads the world and acts, several times a second, forever.

Lines 60–61 — the safety reflex: Before any clever behaviour, in any automatic mode, a close wall stops the wheels. This runs first on purpose: the reflex beats the brain.

Lines 63–69 — dispatch on state: The state machine in action. In follow we grab a frame and steer (unless a wall is close); in avoid we wander; in manual the loop does nothing, because the web routes drive the robot directly. One variable, three behaviours.

Lines 70–72 — clean stop: Ctrl+C stops the motors so the rover never keeps rolling after the program ends.

Note: As written, brain.py is the standalone autonomous program. In the next step we fold this same loop into the Flask app so the web remote and the autonomous brain run together — the loop in a background thread, the web routes flipping STATE["mode"] and driving in manual mode.

Step 5 — A Web Remote

Finally, the controller. We reuse the Flask shape from Lesson 41: routes on the Pi, a styled page in the browser, and JavaScript wiring buttons to those routes. The new routes simply call your Robot and flip the mode. We will also add an optional live video feed.

The Flask server (Python)

Save this as app.py. It runs the control loop in a background thread so the rover keeps thinking while the web server answers requests. Manual-drive routes command the robot directly; the mode route switches the state machine.

# app.py  --  PYTHON: the web remote + the background brain
from flask import Flask, jsonify, render_template, Response
from threading import Thread
import cv2
from gpiozero import DistanceSensor
from robot import Robot
from vision import find_target

app = Flask(__name__)

robot = Robot(left_pins=(20, 21), right_pins=(19, 26))
sonar = DistanceSensor(echo=24, trigger=23, max_distance=2)
cap = cv2.VideoCapture("http://PHONE-IP:8080/video")

STATE = {"mode": "manual"}
CENTRE_X, DEAD_ZONE, NEAR_AREA, STOP_CM = 160, 40, 20000, 20
latest = {"frame": None}      # newest frame, shared with the video feed


def too_close():
    return sonar.distance * 100 < STOP_CM


def control_loop():
    """The brain, run forever in a background thread."""
    while True:
        ret, frame = cap.read()
        if not ret:
            continue
        latest["frame"] = frame
        if STATE["mode"] != "manual" and too_close():
            robot.stop()
            continue
        if STATE["mode"] == "follow":
            cx, area = find_target(cv2.resize(frame, (320, 240)))
            if cx is None:
                robot.stop()
            elif cx - CENTRE_X < -DEAD_ZONE:
                robot.turn_left(0.4)
            elif cx - CENTRE_X > DEAD_ZONE:
                robot.turn_right(0.4)
            elif area < NEAR_AREA:
                robot.forward(0.4)
            else:
                robot.stop()
        elif STATE["mode"] == "avoid":
            robot.forward(0.4)

def index():
    return render_template("remote.html")

def mjpeg():
    """Yield the latest frame over and over as an MJPEG stream."""
    while True:
        frame = latest["frame"]
        if frame is None:
            continue
        ok, buf = cv2.imencode(".jpg", frame)
        if not ok:
            continue
        yield (b"--frame\r\n"
               b"Content-Type: image/jpeg\r\n\r\n" + buf.tobytes() + b"\r\n")


@app.route("/video_feed")
def video_feed():
    return Response(mjpeg(),
        mimetype="multipart/x-mixed-replace; boundary=frame")


if __name__ == "__main__":
    Thread(target=control_loop, daemon=True).start()
    app.run(host="0.0.0.0", port=5000)

Lines 2–7 — imports: Flask's tools (including Response for the video stream and Thread for the background brain), OpenCV, the ultrasonic, and our robot.py and vision.py modules.

Lines 11–13 — the hardware: Build the drive base, the ultrasonic and the camera once, when the app starts.

Lines 15–17 — shared state: The mode dictionary, the tuning numbers on one line, and latest, a tiny store holding the newest frame so the video feed and the brain can share it.

Lines 24–47 — control_loop(): The same brain as brain.py, here as a function. It reads a frame, saves it to latest, applies the safety reflex, then dispatches on the mode. Run in a thread, it loops forever alongside the web server.

Lines 50–52 — / route: Serves the control-pad page from templates/remote.html.

Lines 55–81 — the drive routes: /forward, /left, /right and /stop each switch to manual (so the brain stops fighting you) and command the Robot directly, then reply with a small JSON acknowledgement.

Lines 84–90 — /mode/<name>: One route handles all three modes using a URL variable. It checks the name is valid, flips STATE["mode"], and stops the wheels when returning to manual. This is how the page's mode switch talks to the state machine.

Lines 93–103 — mjpeg(): A generator that yields frames forever. cv2.imencode(".jpg", frame) compresses each frame to JPEG bytes; the yield wraps it in the multipart boundary markers a browser expects. This is the standard Flask MJPEG pattern.

Lines 106–109 — /video_feed: Returns the generator as a Response with the mimetype multipart/x-mixed-replace; boundary=frame — the magic that makes the browser replace the image with each new frame, so an ordinary <img> shows live video.

Lines 112–114 — start-up: Launch the control loop in a daemon thread (it dies with the program), then start Flask on 0.0.0.0:5000 so any device on your Wi-Fi can reach it.

Careful: the Flask development server is single-threaded by default, and the MJPEG feed holds a connection open. If the video makes the buttons feel sluggish, run with app.run(host="0.0.0.0", port=5000, threaded=True) so requests do not queue behind the stream. Keep this server on your home network only — it is not built to face the open internet.

Putting It All Together

Your project folder now holds five files:

├── robot.py        # the drive base (Lesson 42)
├── vision.py       # colour tracking (find_target)
├── brain.py        # standalone autonomous loop (optional)
├── app.py          # the web remote + background brain
└── templates/

Bring it to life in this order, with the wheels off the ground for the first run:

  1. Start the phone camera. Open the IP-webcam app, keep it in the foreground with the screen awake, and note the address it shows. Put that address into app.py's VideoCapture line.
  2. Power the rover. Switch on the separate ~9 V motor pack and power up the Pi on its own supply. Confirm the common ground is connected.
  3. Activate the venv and run the server. source ~/rover/bin/activate, then python app.py. Flask prints Running on http://0.0.0.0:5000.
  4. Open the remote. On your phone (same Wi-Fi), visit http://<pi-ip>:5000 (find the IP with hostname -I) or http://raspberrypi.local:5000. The live feed and buttons appear.
  5. Test manual first. Tap Forward, Left, Right, Stop and watch the propped-up wheels obey. This proves the drive base and the web link before any autonomy.
  6. Try follow. Tap Follow and wave your coloured marker in front of the camera. The wheels should turn to centre it and roll forward as it nears. Tune LOWER/UPPER in vision.py if it ignores your colour.
  7. Try avoid. Tap Avoid and hold your hand in front of the ultrasonic; the rover should spin away rather than into it.
  8. Only now, on the floor. Once every mode behaves with the wheels up, set it down in a clear, open space — never near stairs — and drive for real. STOP is always one tap away.
Tip: The three modes are deliberately layered. Manual proves the hardware, follow proves the vision, avoid proves the sensor — debug them in that order. If follow misbehaves, switch to manual (which stops the brain) before you go chasing the bug.

Safety Checklist

Run down this list before every powered test. It takes ten seconds and saves Pis, fingers and furniture.

  1. Wheels off the ground first. Prop the chassis up for every new run of code, so a bug cannot send the rover off a table or down the stairs.
  2. Separate motor battery. The ~9 V pack powers the motors at the driver's VM — never from the Pi's 5 V pin.
  3. Common ground. Battery −, driver GND, sensor GND and Pi GND all meet at one rail. No common ground, no working rover.
  4. Never feed motor voltage into the Pi. The motors' white/black wires touch only the driver outputs. A stalled motor's ~1 A or its switch-off spike would destroy a GPIO pin.
  5. Level-shift the ECHO line. The HC-SR04's 5 V ECHO reaches GPIO 24 only through its 330 Ω/470 Ω divider.
  6. Two kill switches. The web STOP button halts the wheels and returns to manual; Ctrl+C in the terminal ends the program (and the except KeyboardInterrupt stops the motors). Know where both are before you drive.
  7. Mind heat and current. If the driver chip gets hot or the motors stall against an obstacle, cut power — a stalled motor draws its full ~1 A and heats the driver. The DRV8833 handles it briefly, but do not leave a rover pushing against a wall.
  8. Power off to rewire. Shut down and unplug the Pi before any wiring change; re-power only after a full check.
Careful: the rover can move on its own in follow and avoid modes. Keep it away from stairs, ledges, pets and small children during testing, and keep your phone in hand with STOP ready. An autonomous robot that you cannot instantly stop is not ready to be on the floor.

Make It Your Own / Where to Go Next

You have fused four salvaged subsystems into one robot that sees, thinks, dodges and obeys — almost entirely from the e-waste pile. Here is where to take it next:

  • Line following. Point the phone camera (or a swapped-in light sensor) at the floor and steer to keep a dark line centred — the very same "offset → turn" logic as follow mode, with no colour or AI model needed.
  • Swap colour tracking for object detection. Replace find_target with the TensorFlow Lite or IMX500 detector from Lessons 19 and 42 to follow a person or a named object regardless of colour. The control loop never changes — only the function that produces cx.
  • Voice control. Add the speech work from Lesson 19 so "follow me", "stop" or "explore" flip STATE["mode"] with your voice instead of a button.
  • Simple mapping with the encoders. Read the NXT motors' built-in encoders (the RotaryEncoder from Lesson 42) to count how far each wheel has turned, so the rover can drive set distances or even sketch a rough map of where it has been.
  • Go EV3. LEGO's newer EV3 motors and sensors use the same RJ12 plug and the same ideas; with the DIY wiring or a BrickPi3 you can reuse those too.
  • Share your build. Post your code, your wiring photos and your tuned HSV values on the Raspberry Pi forums or your own blog. A junkbox rover is exactly the kind of project the community loves — and someone else's spare parts pile is waiting for your idea.
Tip: Keep robot.py and vision.py as your reusable foundation. Every extension above — line follower, voice rover, mapper — just imports them and gives new orders. That is the real lesson of modules and classes: write the hard part once, and reuse it forever.

Key terms

  • Module / import - a Python file you reuse from another with from robot import Robot; write the hard part once, import it everywhere.
  • State machine - a program always in one state (manual/follow/avoid), held in a dictionary, that behaves differently in each and switches on events.
  • Main control loop - the while True: heartbeat that reads the world, decides, and acts, several times a second.
  • HSV colour tracking - convert a frame to HSV, cv2.inRange to a mask, findContours for the biggest blob, moments for its centre (cx).
  • Centroid / steering error - the blob's centre x minus the frame's middle; its sign tells the rover which way to turn.
  • VideoCapture(url) - OpenCV reading the phone's MJPEG Wi-Fi stream as if it were a video file.
  • MJPEG / multipart/x-mixed-replace - the Flask streaming trick that lets a plain <img> show live video by replacing it frame by frame.
  • Safety reflex - the ultrasonic stop that overrides every mode; a reflex that beats the brain.
  • Separate battery + common ground - motors on their own ~9 V pack, but its negative joined to the Pi's ground as one 0 V reference.
