You already met permissions in the beginner lesson — the friendly rwx triad and a little octal arithmetic. This chapter goes deeper into the part that actually trips people up and matters for security: how permissions behave on directories, the three "special bits" that bend the normal rules, why a single setuid binary can hand away the keys to the whole Pi, and the modern tools — capabilities, a carefully written sudoers, and PAM — that replace the old all-or-nothing idea of "root". Your Pi 5 runs full Debian with systemd and bash, so everything here is real and everything here is yours to break. Take your time; this is genuinely interesting once it clicks.

Careful: This lesson has you edit the sudoers file and build a setuid binary — two of the few things on a Linux box that can lock you out of your own administrator account or open a real security hole. Do the risky steps on a spare microSD card or a fresh Raspberry Pi OS install, not the Pi you rely on day to day. Each risky project below is flagged with a ⚠️.

The bits, fast (a quick recap)

Every file and directory carries a 10-character mode that ls -l prints: a type character followed by three triads — user, group, other — each made of r (read = 4), w (write = 2), and x (execute = 1). Add the numbers per triad and you get the octal form you set with chmod.

-rwxr-x---   means   user rwx (7)   group r-x (5)   other --- (0)   =   chmod 750

That much you know. The interesting wrinkle — and the bridge into everything else in this lesson — is that on a directory the very same three bits mean something completely different.

What rwx means on a directory

  • x (execute) on a directory = the right to traverse it — to cd into it and reach files inside by name. Without x you cannot touch anything in the directory even if you know it is there.
  • r (read) on a directory = the right to list the names inside it (what ls shows). You can have x without r: you can open files whose names you already know, but you cannot list what is there.
  • w (write) on a directory = the right to create, delete, or rename entries inside it.
In plain words: A directory is really just a list of names that point to files. Permissions on the directory control who may edit that list — not the contents of the files the list points to.

The delete surprise: you can erase a file you can't write

This is the single most surprising consequence of the rule above, and it catches almost everyone the first time.

Myth vs reality: Myth — "I can't delete a file unless I'm allowed to write to it." Reality — deletion is a directory operation. To remove reports/secret.txt you need w and x on reports/ — the file's own permissions are completely irrelevant. You can delete a read-only file you don't even own, as long as you can write its directory. And the mirror image is just as true: you can be unable to delete a file you fully own if its directory is not writable by you.

The key insight: a file's name does not live in the file — it lives in the directory. Removing a name is editing the directory's list, so the directory's permissions are what the kernel checks. (You'll see why in the next lesson on filesystems, where names and files are truly separate things.) The sticky bit, coming up shortly, exists precisely to tame this behaviour in shared folders like /tmp.

The special bits: where it gets interesting

Above the familiar nine permission bits sit three more, the "special bits". Each one changes the rules in a focused, powerful way.

  • setuid (u+s, octal 4000) — when set on an executable, the program runs with the file owner's identity instead of the identity of whoever launched it. The classic example is /usr/bin/passwd: it is owned by root and setuid, so an ordinary user can change their password — which means editing the protected file /etc/shadow — but only through passwd's narrow, carefully written logic.
  • setgid (g+s, octal 2000) — on a file, the program runs with the file's group. On a directory it does something far more useful: every new file created inside inherits the directory's group rather than the creator's primary group. This is the trick behind shared team folders.
  • sticky bit (+t, octal 1000) — on a directory, only a file's owner (or root) may delete or rename it, even when the directory itself is world-writable. This is exactly the fix for the "delete surprise" above.
ls -ld /tmp                 # drwxrwxrwt   -- note the trailing 't': sticky bit
ls -l  /usr/bin/passwd      # -rwsr-xr-x   -- note the 's' in the user triad: setuid
chmod 2775 shared/          # setgid directory: new files inherit its group
Note: An uppercase S or T in ls -l means the special bit is set but the matching execute bit is not — usually a mistake worth a second look. A lowercase s/t means both are set, which is normally what you want.

Why /tmp uses the sticky bit

/tmp is world-writable so any program, run by any user, can drop a scratch file there. Without the sticky bit, "world-writable directory" would mean anyone can delete anyone else's files — exactly the delete surprise, weaponised. The trailing t on drwxrwxrwt restricts deletion to each file's owner, so everyone can create freely but nobody can clobber a neighbour's work.

Why setuid is a security minefield

A setuid-root binary is, in plain terms, a privilege boundary you have handed to every unprivileged user on the machine. The instant that program starts, it is root — so any flaw in it becomes a path to full root access. A buffer overflow, a command injection, blindly trusting $PATH or $IFS, or following a symlink it shouldn't: each can turn an ordinary user into the administrator of your Pi.

Because the stakes are so high, three things are worth burning into memory:

  1. The whole industry is moving away from setuid toward fine-grained capabilities (next section), which hand out one slice of root's power instead of all of it.
  2. The Linux kernel ignores the setuid bit on scripts. A timing race around the #! shebang made setuid scripts hopelessly unsafe, so only compiled binaries honour the bit. A "setuid shell script" silently runs with your normal privileges.
  3. You should periodically audit what is setuid on your system and ask whether each one truly needs to be.
find / -perm -4000 -type f 2>/dev/null     # list every setuid binary on the Pi
The -perm -4000 test matches any file whose setuid bit is set (the leading - means "at least these bits"). -type f limits it to regular files, and 2>/dev/null throws away the "permission denied" noise from directories you can't read so the real results stand out.

umask: the bits you remove

umask isn't a permission you grant — it's a mask that is subtracted from the defaults whenever a new file or directory is created. Files start from 666 and directories from 777 (no execute on plain files by default), and the umask carves bits away from that starting point.

umask                 # show the current mask (commonly 022 on the Pi)
# umask 022  ->  new files become 644, new directories 755   (the usual default)
# umask 077  ->  new files become 600, new directories 700   (private: owner only)
# umask 002  ->  keeps group-write on, which pairs nicely with a setgid shared dir
Tip: A umask of 077 is a quick way to make everything you create from that shell readable only by you — handy when you're handling keys or personal data on a shared Pi.

Capabilities: splitting root into ~40 pieces

The deepest fix for the setuid problem is to stop treating "root" as a single switch. Modern Linux decomposes root's powers into roughly forty discrete capabilities, so a process can be granted only the one tiny power it actually needs and nothing else.

Capability What it lets a process do
CAP_NET_BIND_SERVICE Bind to ports below 1024 without being root — this kills the old "run nginx as root just to listen on port 80" anti-pattern.
CAP_NET_RAW Open raw network sockets (how ping works).
CAP_DAC_OVERRIDE Bypass the normal file read/write/execute permission checks.
CAP_SYS_ADMIN The dangerous catch-all grab-bag — so broad you should treat it as "basically root". 
# Grant just one capability to a binary instead of making it setuid-root:
sudo setcap 'cap_net_bind_service=+ep' /usr/local/bin/myserver
getcap /usr/local/bin/myserver
sudo getcap -r / 2>/dev/null            # audit: what on this Pi already has capabilities?
In plain words: A capability is a single named power that used to belong only to root. Instead of giving a program all of root, you hand it the one key it needs — like letting a delivery driver into the lobby without giving them the master key to every flat.

The key insight: setuid-root says "be the all-powerful administrator and please behave"; a capability says "you may do exactly this one thing and nothing more". The second is a smaller, safer promise. The even better pattern is to declare capabilities per service in systemd (you'll meet systemd properly later) using AmbientCapabilities=, CapabilityBoundingSet=, and NoNewPrivileges=true — that keeps the policy centralised and auditable, with no special bits living loose on binaries, and the bounding set hard-caps what the service could ever acquire.

sudo and sudoers: least privilege for humans

sudo runs a single command as another user — root by default — after checking the rules in /etc/sudoers and its drop-in directory /etc/sudoers.d/. The grammar reads like a sentence: who may run what, where, and as whom.

# /etc/sudoers.d/deploy   -- a drop-in file; never hand-edit /etc/sudoers directly
deploy  ALL=(root) NOPASSWD: /usr/bin/systemctl restart myapp, /usr/bin/journalctl -u myapp
#  who   host=(runas)  option    exactly which commands, by absolute path
Read it left to right: the user deploy, on any host (ALL=), may run as root, without typing a password (NOPASSWD:), only the two exact commands listed. Anything else is refused. Naming the full absolute path matters — without it, a different program with the same name earlier on $PATH could be substituted.
Careful — always use visudo: Edit sudoers only through sudo visudo (or sudo visudo -f /etc/sudoers.d/deploy for a drop-in). It syntax-checks the file before saving and refuses to write a broken one. A single stray character in sudoers can lock you out of sudo entirely — and since the Pi's root account has no password, that can mean no administrator access at all until you boot from another card to repair it.
Careful — never NOPASSWD a pager or editor: Do not grant passwordless sudo on anything with a built-in shell escape — editors (vim, nano), pagers (less, more, man), and tools like find, awk, tar, or any language interpreter. Each can spawn a root shell from inside itself, turning a narrow grant into full root. Cross-check every sudo rule you write against GTFOBins, a catalogue of exactly these escapes.
Tip: Run sudo -l to print everything the current user is allowed to run via sudo. It's the fastest way to review a grant — yours or a teammate's — before trusting it.

PAM: why login logic isn't hardcoded

Here's a question worth pausing on: login, sshd, sudo, and su all need to check "is this person who they claim to be?" — yet none of them contains its own password-checking code. They all call out to PAM (Pluggable Authentication Modules), which consults a stack of small modules defined per program in /etc/pam.d/, across four phases:

  • auth — who are you? (password, SSH key, a 2FA token, a fingerprint)
  • account — are you allowed right now? (account expired? login restricted to certain hours?)
  • password — the rules for changing the secret (length, complexity, history)
  • session — set-up and tear-down: mount the home directory, apply resource limits with pam_limits, write the login to the logs

The key insight: because every login program defers to the same PAM stack, you can add two-factor authentication, LDAP logins, or per-user resource limits to all of them at once — without touching sshd or sudo at all. You edit the policy, not the programs. It's the same "a layer of indirection solves it" idea you keep meeting in Linux, applied to authentication itself.

Try it on your Pi

  1. Build a shared team folder with setgid. Create two users and a shared group: sudo adduser alice, sudo adduser bob, sudo groupadd team, then add both with sudo usermod -aG team alice (and the same for bob). Make a folder sudo mkdir /srv/team, give it the group with sudo chgrp team /srv/team, and set sudo chmod 2775 /srv/team — the leading 2 is the setgid bit. Log in as alice, create a file, then log in as bob and confirm the file belongs to group team and bob can edit it. (Add umask 002 in each user's shell so new files stay group-writable.)
  2. Reproduce the /tmp sticky-bit behaviour, then escape it with an ACL. Make a world-writable folder sudo mkdir /srv/scratch && sudo chmod 1777 /srv/scratch — the leading 1 is the sticky bit. As alice create a file there; as bob confirm you cannot delete it. Then grant one specific extra user access with an ACL: setfacl -m u:carol:rw somefile, read it back with getfacl somefile, and notice the + that now appears in ls -l — your sign that an ACL is in play beyond the normal owner/group/other.
  3. ⚠️ Lock down sudo with a drop-in. Using sudo visudo -f /etc/sudoers.d/deploy, give a deploy user NOPASSWD on only restarting one service and reading its logs — nothing else. Switch to deploy, run sudo -l to confirm the grant, then deliberately try to break out (for example by getting a pager to spawn a shell) and confirm you can't. Audit your rule line against GTFOBins. Do this on a spare card so a sudoers mistake can't strand you.
  4. ⚠️ Write a safe setuid demo, then watch the kernel refuse a script. Write a tiny C program that does one narrow privileged thing and immediately drops back to its real UID; compile it, sudo chown root, and sudo chmod u+s it. Print getuid() versus geteuid() to see real, effective, and saved UIDs split apart — the same model passwd uses. Then make a setuid shell script, run it, and confirm it runs with your ordinary privileges: proof the kernel ignores the setuid bit on scripts. Build this on a spare install, never on a Pi you depend on.

Key terms

  • Directory execute (traverse) bit - The x permission on a directory: the right to enter it and reach files inside by name, separate from the r bit that lists names.
  • setuid - A special bit (octal 4000) that makes an executable run as its file owner rather than the caller; how passwd can edit /etc/shadow as root. Ignored on scripts.
  • setgid - A special bit (octal 2000); on a directory it makes new files inherit the directory's group, the basis of shared team folders.
  • sticky bit - A special bit (octal 1000) on a directory that lets only a file's owner (or root) delete it, even when the directory is world-writable; why /tmp is safe.
  • umask - A mask of permission bits subtracted from the defaults (666 for files, 777 for directories) when something new is created.
  • capability - One named slice of root's power (e.g. CAP_NET_BIND_SERVICE) that can be granted alone, the modern, safer alternative to setuid-root.
  • sudoers / visudo - The policy file defining who may run what via sudo, and the editor that syntax-checks it before saving so a typo can't lock you out.
  • GTFOBins - A catalogue of common binaries (editors, pagers, archivers) that contain shell escapes, used to spot dangerous sudo grants.
  • PAM (Pluggable Authentication Modules) - The stacked framework that login, sshd, sudo, and su all call for authentication, so policy changes apply everywhere at once.
  • ACL (Access Control List) - The escape hatch (setfacl/getfacl) for granting one specific user or group access beyond the three owner/group/other classes; shown by a + in ls -l.
