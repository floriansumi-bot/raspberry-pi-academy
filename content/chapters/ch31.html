By now you have used Docker in this course — to self-host a service, to run something without polluting your Pi's main system. It probably felt a little like magic: one command, and suddenly there's a tidy, isolated little Linux inside your Linux. This lesson pulls the curtain back. We are going deeper, and demystifying Docker completely. Here is the secret, stated plainly up front: a container is not a special kind of thing. It is an ordinary process — just like the ones you have started a hundred times — that the kernel has placed into some clever boxes called namespaces and cgroups. Your Pi 5 runs a full 64-bit Linux kernel with all of these primitives built in, so you can assemble a container by hand, with nothing but commands you already half-know. After this, Docker will never feel like magic again — it will feel like a very nice convenience wrapper, which is exactly what it is.

Careful: The hands-on parts of this lesson create new namespaces, chroot into a downloaded filesystem, and write limits into kernel control files. None of it is exotic, but it does need sudo and it does touch low-level kernel machinery. Do it on a Pi you are happy to experiment with — a spare microSD card or a fresh Raspberry Pi OS install — not the one running anything you care about. Every command here is reversible by simply exiting the shell or rebooting, but read before you paste.

What a container really is

Reach for the most ordinary mental picture of a running program: a process, with a number (its PID), reading and writing files, owning some memory, maybe holding a network connection. That is the whole starting point. To turn that ordinary process into "a container", Linux does two separate jobs:

  • Namespaces change what the process can see. They give it a private view of one slice of the system — its own process list, its own network, its own filesystem tree — so that from the inside it looks like it has the whole machine to itself.
  • cgroups change what the process can use. They cap how much CPU, memory, or I/O the process (and its children) are allowed to consume, so one container cannot starve the others.

Add a swapped-in root filesystem — a little self-contained userland to live in — and that's it. That's a container.

The key insight: There is no "container" object anywhere in the Linux kernel. You will never find a create_container() system call. Docker, Podman, and Kubernetes are orchestration glue wrapped around primitives — namespaces, cgroups, a root filesystem — that you can drive by hand. The kernel does not know the word "container". It only knows processes that happen to be wearing some isolation.
In plain words: A container is a process in a costume. The costume (namespaces) changes what it sees in the mirror; a leash (cgroups) limits how much it can eat. Underneath the costume it is the same kind of process as everything else on your Pi.

Namespaces: isolating what a process can see

A namespace virtualises one kind of global kernel resource, so the processes inside get their own private version of it. There are eight of them, and each isolates exactly one thing:

Namespace Isolates Effect inside
mnt (mount)the mount tableits own filesystem tree
pidprocess IDsits first process is PID 1; cannot see host processes
netthe whole network stackown interfaces, routes, firewall, ports
userUID / GID mappingsroot inside (UID 0) maps to an unprivileged UID outside
utshostname / domainnameits own hostname
ipcSysV / POSIX IPCisolated shared memory and message queues
cgroupthe cgroup root viewhides the host's cgroup hierarchy
timeboot / monotonic clock offsets(newest; kernel 5.6+, which your Pi 5 has)

Mix and match them. Docker hands a container a fresh set of most of these; a lightweight sandbox might use only one or two. They are independent dials.

The security keystone: the user namespace

Of the eight, the user namespace is the one to understand deeply, because it is what makes containers genuinely safe rather than merely tidy. Inside a user namespace, a process can be UID 0 — "root" — with all the apparent powers of root, while on the host that same process maps to a powerless, high-numbered UID that owns nothing important.

The consequence is large: even if an attacker breaks out of a container, they do not land as root on your Pi. They land as nobody. This is exactly what makes rootless containers possible — Podman and rootless Docker let an ordinary, unprivileged user run containers without ever touching real root.

In plain words: "root" inside a rootless container is a stage costume, not real power. The actor is allowed to play the king on stage (inside), but the moment they walk off into the street (the host) they are an ordinary citizen again. A breakout hands the attacker the costume, not the crown.

cgroups v2: limiting what a process can use

Where namespaces isolate visibility, cgroups (control groups) limit and account resources: CPU, memory, I/O, and the number of processes. Modern systems — including current Raspberry Pi OS — use cgroup v2, a single unified hierarchy that is far cleaner than the old v1 tangle of one separate tree per resource.

The beautiful part is how plain the interface is. cgroups are a filesystem. You create a control group by making a directory, and you set limits by writing numbers into files:

# Create a cgroup, cap it at 50% of one CPU and 100 MB, run a process inside it:
sudo mkdir /sys/fs/cgroup/demo
echo '50000 100000' | sudo tee /sys/fs/cgroup/demo/cpu.max      # 50ms per 100ms = half a core
echo $((100*1024*1024)) | sudo tee /sys/fs/cgroup/demo/memory.max
echo $$ | sudo tee /sys/fs/cgroup/demo/cgroup.procs             # move THIS shell into it
# now anything you run here is throttled to half a core and OOM-killed past 100 MB
mkdir /sys/fs/cgroup/demo — creating the directory is creating the cgroup; the kernel populates it with control files automatically.
cpu.max = "50000 100000" — allow 50,000 microseconds of CPU time per 100,000-microsecond window, i.e. 50% of one core.
memory.max — a hard ceiling in bytes; cross it and the kernel OOM-kills a process in the group.
echo $$ > cgroup.procs — $$ is the current shell's PID; writing it here moves this shell (and everything it later launches) into the group.

Two cgroup-v2 rules are worth remembering: processes may only live in leaf cgroups (the "no internal processes" rule), and each controller is switched on top-down through a file called cgroup.subtree_control.

Note: When Docker says --memory=100m or --cpus=0.5, this is literally what it does under the hood — write those exact numbers into a cgroup it created for your container. No magic, just file writes.

unshare and nsenter: containers by hand

Two small command-line tools let you drive namespaces directly, and they are perfect mirror images of each other:

  • unshare — creates new namespaces and runs a process inside them. This is how you build a container.
  • nsenter — enters existing namespaces of a process that is already running. This is how you debug a container — even one so minimal it has no shell or tools of its own.
# Become PID 1 in your own pid + mount + user namespace, "root" but unprivileged on the host:
unshare --user --map-root-user --pid --mount --fork bash
#   inside:  id      -> uid=0(root)      (a fake, mapped root)
#            ps aux  -> almost nothing   (its own pid namespace)

# From the host, enter a running container's network namespace to inspect its sockets:
sudo nsenter -t <pid> -n ss -tlnp
unshare --user --map-root-user — make a new user namespace and map your UID to 0 inside it (rootless "root").
--pid --mount --fork — also new PID and mount namespaces; --fork is required because the process that creates a PID namespace is not itself in it — its child becomes PID 1.
nsenter -t <pid> -n — join the network namespace (-n) of the process with PID <pid>, then run ss -tlnp there to list its listening sockets. Replace <pid> with the real PID.
Tip: nsenter is the single most useful trick for debugging real Docker containers. A container built FROM scratch may have no shell at all — but you can still step into its network or mount namespace from the host with nsenter and use the host's tools to look around.

Assemble a container by hand

Here is the recipe Docker automates, in full: new namespaces + a root filesystem + cgroup limits, then exec your program. The only piece we have not gathered yet is the root filesystem — a tiny userland for the process to live in. We will use Alpine Linux, which ships a minimal root filesystem that is only a few megabytes.

Careful — get the right architecture. Your Raspberry Pi is ARM, not x86. You must download the aarch64 (ARM64) Alpine rootfs, not the x86_64 one you'll see in most internet tutorials. An x86_64 binary simply will not run on the Pi's CPU. Look for a file named like alpine-minirootfs-3.20.0-aarch64.tar.gz.
# 1. Get a tiny ARM64 root filesystem for the Pi:
mkdir alpine-root && cd alpine-root
curl -sL https://dl-cdn.alpinelinux.org/alpine/latest-stable/releases/aarch64/alpine-minirootfs-3.20.0-aarch64.tar.gz | tar xz
cd ..

# 2. New PID + mount namespaces, chroot into the rootfs, remount /proc, exec a shell:
sudo unshare --pid --fork --mount-proc \
  chroot alpine-root /bin/sh
#   inside: you are PID 1, you see only the Alpine userland, /proc reflects only your namespace
curl ... aarch64 ... | tar xz — download the ARM64 Alpine mini rootfs and unpack it straight into alpine-root/.
unshare --pid --fork — new PID namespace; the forked child becomes PID 1 inside it.
--mount-proc — also new mount namespace, with a fresh /proc mounted so tools like ps reflect this namespace, not the host's.
chroot alpine-root /bin/sh — switch the root directory to the Alpine tree and run its shell. Inside, echo $$ prints 1 and ps sees almost nothing.

That is a container. Add a network namespace and a veth pair for networking, write CPU and memory limits into a cgroup as shown above, and swap chroot for pivot_root (which gives proper, leak-free mount isolation), and you have reproduced the core of docker run. What Docker adds on top is genuinely valuable — images (layered, content-addressed filesystems stacked with overlayfs), a registry to pull them from, automatic networking, and a friendly UX — but none of it is a secret kernel feature. It is all convenience over the primitives you just used.

In plain words: overlayfs lets Docker stack read-only image layers under a thin writable layer, so a hundred containers can share one base image without copying it a hundred times. It is the same kind of mount trick you met with filesystems — Docker just automates the stacking.

PID 1, and why containers need an init

There is one consequence of all this that bites people in production, and it follows straight from the process model. In a normal Linux system, PID 1 is init (systemd on your Pi), and it has two special duties: it reaps orphaned zombie processes, and it forwards signals sensibly. Inside a container with its own PID namespace, your application is PID 1 — and it probably was not written to do those jobs.

Two things go wrong as a result:

  • If your app ignores SIGTERM (many do, by default, when they are PID 1), then docker stop waits ten seconds and then SIGKILLs it — an ungraceful, abrupt shutdown every time.
  • If your app spawns children and does not reap them, the zombies pile up, because there is no real init underneath to clean them away.

The key insight: this is exactly why docker run --init exists — it injects a tiny, correct init process (such as tini or dumb-init) as PID 1, which reaps zombies and forwards signals so your app does not have to. The flag is not a workaround for a Docker quirk; it is the same PID-1 responsibility from ordinary Linux, surfacing in a place you did not expect.

Try it on your Pi

Docker on a Raspberry Pi is hugely popular, and now you can see the primitives it sits on. Work through these in order on a spare microSD card or fresh install.

  1. Map the namespaces. Without running anything risky, write down all eight namespaces and, for each, one sentence on what it isolates plus one real consequence (for example, "user ns → rootless containers"). Then run lsns to list the namespaces live on your Pi and notice which processes share which.
  2. One-command mini-container. Download the aarch64 Alpine rootfs as shown above, then run sudo unshare --pid --fork --mount-proc chroot ./alpine-root /bin/sh. Inside, confirm you are PID 1 with echo $$, that ps sees almost nothing, and that your hostname and mounts are isolated. Then answer for yourself: why did /proc have to be remounted?
  3. Limit it with cgroups v2. Create /sys/fs/cgroup/demo, set cpu.max and memory.max, drop a CPU-hungry process into it (even yes > /dev/null works), and watch the throttling in top. Then push a process past memory.max and find the OOM-kill recorded in dmesg. Resource control as nothing but file writes.
  4. Hand-assemble, then compare to Docker. Combine namespaces (add a network namespace and a veth pair if you are feeling brave), a pivot_root into the rootfs, and a cgroup with limits, all in one script that ends by execing a shell. Then run the same workload with docker run and enumerate exactly what Docker added on top of your script. Nothing demystifies containers faster than this side-by-side.

Key terms

  • Container — not a kernel object, but an ordinary process placed into namespaces and cgroups, usually with its own root filesystem.
  • Namespace — a kernel feature that gives a process a private view of one global resource (processes, network, mounts, users, hostname, IPC, cgroups, or time).
  • cgroup v2 — control groups in their unified hierarchy; limit and account CPU, memory, I/O, and process count via files under /sys/fs/cgroup.
  • User namespace — the namespace that maps in-container UID 0 to an unprivileged host UID; the security keystone that makes rootless containers safe.
  • Rootless container — a container run by an unprivileged user (Podman, rootless Docker), where in-container "root" has no real power on the host.
  • unshare — the command that creates new namespaces and runs a process inside them; how you build a container by hand.
  • nsenter — the command that enters the existing namespaces of a running process; how you debug a container from the host.
  • chroot / pivot_root — swap the root filesystem for a process; pivot_root is the proper, leak-free version Docker uses.
  • overlayfs — the layered, copy-on-write filesystem Docker stacks image layers with, so many containers share one base image.
  • PID 1 / init (tini) — the first process in a PID namespace; it must reap zombies and forward signals, which is why docker run --init injects a small init like tini.
  • cpu.max / memory.max — the cgroup-v2 control files that cap CPU quota and memory; what --cpus and --memory write to under the hood.
