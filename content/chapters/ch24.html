You have heard the famous Unix slogan: "everything is a file." It sounds mystical, but it hides one of the most beautiful ideas in computing — and your Raspberry Pi 5 uses it constantly. This is the "going deeper" track: the same warm explanations as before, but now we lift the lid and look at how it really works underneath.

The Real Slogan: Everything Is a File Descriptor

"Everything is a file" does not mean every single thing is literally a file sitting on your microSD card. It means that wildly different things — a text file, your keyboard, the screen, a network connection, even live information from inside the Linux kernel — are all reached through the same small set of operations: open, read, write, close. One toolkit, over many different kinds of object. That uniformity is the deepest idea in Unix, and it is why one command can pipe into another no matter what they actually do.

The handle that ties all of this together is called a file descriptor.

In plain words: A file descriptor (FD) is just a small whole number — like a ticket number — that your program holds while it has something open. The kernel keeps the real details (which file, where you are up to, read or write); your program only ever waves the little number around and says "read from number 3" or "write to number 1."

Every program on your Pi starts life with three file descriptors already open by convention:

FD number Name Where it points by default
0 stdin (standard input) Your keyboard
1 stdout (standard output) Your terminal
2 stderr (standard error) Your terminal

That split between FD 1 (normal results) and FD 2 (errors) is why you can save a program's output to a file while still seeing its error messages on screen. They travel down two separate pipes.

Myth vs reality: The myth says "everything is a file, so I can open() a network socket by its path." Reality: network sockets are the famous exception — you create them with a special socket() call, not by opening a path. So the precise slogan is "everything is a file descriptor." Once you have the descriptor, reading and writing work the same way for everything. How you first get the descriptor is what differs.

Redirection Is File-Descriptor Surgery

When you type cmd > out.txt, the > does not magically "send output to a file." What actually happens is that your shell quietly rewires file descriptor 1 to point at out.txt before your program even starts running. The program then writes to FD 1 as usual, blissfully unaware that "the terminal" is now a file.

cmd > out.txt          # point FD 1 (stdout) at out.txt
cmd 2> err.txt         # point FD 2 (stderr) at err.txt
cmd > out.txt 2>&1     # FD 1 -> the file, THEN FD 2 -> "wherever 1 points now"
cmd 2>&1 > out.txt     # FD 2 -> "wherever 1 points now", THEN FD 1 -> file. DIFFERENT!

2>&1 reads as: "make file descriptor 2 a copy of whatever file descriptor 1 refers to at this exact moment." The key word is moment — it is a snapshot, not a permanent link.
In the third line, FD 1 is sent to the file first, so when 2>&1 runs, FD 2 copies "the file." Both end up in out.txt. Good.
In the fourth line, the order is flipped. 2>&1 runs while FD 1 still points at the terminal, so FD 2 becomes "the terminal." Only then does FD 1 move to the file. Result: errors still go to your screen, normal output goes to the file. Same characters, opposite effect.

The key insight: redirections are applied strictly left to right, and 2>&1 copies wherever FD 1 points right now. Order matters. To capture both streams into one file, put the redirection of FD 1 first: cmd > out.txt 2>&1. Bash also offers the shorthand cmd &> out.txt, which means "both streams to this file."

Note: Why can the shell do this surgery before your program runs? Because of how Linux launches programs (the fork-then-exec model, covered in the next lesson). The shell makes a child, rearranges the child's descriptors 0, 1 and 2, and only then loads your program. Your program inherits the new wiring and never knows it was changed.

The sudo ... > file Trap

This trips up almost everyone at least once on their Pi:

sudo echo "dtparam=on" > /boot/firmware/config.txt     # FAILS: Permission denied
echo "dtparam=on" | sudo tee -a /boot/firmware/config.txt  # works

In the first line, sudo only elevates the echo command. But the redirection > is performed by your shell, running as you, before sudo ever starts. Your ordinary user cannot open that protected file, so it fails.
In the second line, tee itself runs under sudo (as root), so it is tee that opens the file — and root is allowed. The -a appends instead of overwriting. This is the idiom for writing to a root-owned file.

Careful: Files like /boot/firmware/config.txt control how your Pi boots. Practise this redirection idea on a throwaway file in your home folder first, and ideally experiment on a spare microSD card you can re-flash, so a mistake never touches your working system.

Pipes: Concurrency and Automatic Flow Control

When you write a | b, the shell creates a small in-memory buffer in the kernel (around 64 KiB) and wires a's stdout straight into b's stdin. A pipe is never a file on your card — it exists only as a pair of file descriptors.

Here is the lovely part: a and b run at the same time. If b is slow and the buffer fills up, a simply pauses until b catches up. You get automatic flow control — what engineers call backpressure — completely for free, with no effort from you.

# The Unix philosophy in one line: small tools, composed.
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head
#   extract column 1     | group | count | rank   | top 10

Five tiny tools, each doing one job, chained into something powerful. awk pulls out the first field of each line; sort groups identical lines together; uniq -c counts the duplicates; sort -rn ranks them highest-first; head shows the top few. None of them knows about the others. That is the whole magic of pipes.

Why cmd | while read "Forgets" Your Variables

This is a classic Pi-scripting head-scratcher. You expect a count, and you get zero:

count=0
grep error /var/log/syslog | while read -r line; do
    count=$((count + 1))
done
echo "$count"     # prints 0  -- but why?!
Myth vs reality: The myth is "the loop ran, so count must have changed." Reality: each stage of a pipeline runs in its own separate child process (a subshell). The while loop incremented count inside that child. When the child finished, its memory — and your new count — vanished with it. The parent shell's count was never touched.

Two clean fixes, both worth knowing:

# Fix 1: process substitution, so the loop runs in YOUR shell, not a child
count=0
while read -r line; do
    count=$((count + 1))
done < <(grep error /var/log/syslog)
echo "$count"     # correct count

# Fix 2: tell bash to run the last pipeline stage in the parent
shopt -s lastpipe
count=0
grep error /var/log/syslog | while read -r line; do count=$((count + 1)); done
echo "$count"

Fix 1 replaces the pipe with < <(...) (process substitution, explained just below). The loop now runs directly in your shell, so the variable survives.
Fix 2 uses shopt -s lastpipe, a bash option that runs the final stage of a pipeline in the parent shell instead of a child. It works in scripts where job control is off.

tee: Splitting a Stream in Two

tee is the plumber's T-joint. It reads its input, writes a copy to one or more files, and passes the same data straight through to the next command. You see it on screen and save it to disk at once.

sudo apt full-upgrade 2>&1 | tee upgrade.log | grep -i error
echo "some config" | sudo tee /etc/myapp.conf
sensors 2>&1 | tee -a temps.log

Line 1: run a big upgrade, fold its errors into the same stream with 2>&1, save everything to upgrade.log, but only show lines containing "error" on screen. Nothing is lost.
Line 2: the write-to-a-root-owned-file idiom from earlier — tee runs as root and opens the file.
Line 3: -a appends to the log instead of overwriting it, so each run adds to the history.

Process Substitution: Turning a Command Into a "Filename"

Half of the Unix tools on your Pi read from standard input. The other half insist on being handed a filename as an argument. Process substitution is the clever adapter that bridges the two worlds.

When you write <(cmd), the shell runs cmd and hands the next program a special filename (really something like /dev/fd/63) that, when read, delivers cmd's output. The other program thinks it is reading an ordinary file — but there is no file, just a pipe wearing a filename costume.

diff <(sort a.txt) <(sort b.txt)          # compare two sorted lists, no temp files
comm -13 <(sort old.txt) <(sort new.txt)  # show only the lines new to new.txt
while read -r x; do echo "$x"; done < <(produce)   # the pipeline-variable fix
some_cmd > >(tee run.log)                  # OUTPUT substitution: tee a stream inline

diff wants two filenames, but you want to compare two sorted lists. Process substitution gives diff two "files" that are actually live sort outputs — no temporary files to create or clean up.
The last line flips it around: > >(tee run.log) is output process substitution. It sends a command's output into the tee process as if writing to a file.

The key insight: <(...) exists precisely because some tools speak "stdin" and others speak "file path." It is the universal translator between the two.

Windows Into the Kernel: /dev, /proc and /sys

Here is where "everything is a file" becomes genuinely magical on your Pi. Three special folders — /dev, /proc and /sys — look like normal directories, but they are virtual filesystems. The files inside them do not exist on your microSD card. The kernel invents their contents on the spot, every time you read them. They are how you inspect and control the whole system with nothing more than cat and echo.

cat /dev/null                       # the "bit bucket" -- anything sent here disappears
head -c 16 /dev/urandom | xxd       # 16 bytes of real kernel randomness, as a "file"

ls -l /proc/self/fd/                # YOUR process's open file descriptors, as symlinks
cat /proc/cpuinfo                   # live details of your Pi 5's four CPU cores
cat /proc/meminfo                   # live memory usage, no special tool needed
readlink /proc/$$/exe               # the path to the shell binary you are running now

cat /sys/class/net/*/operstate      # are your network interfaces up or down?
cat /sys/class/thermal/thermal_zone0/temp   # your Pi's CPU temperature, in milli-degrees

/dev/null is the void — write to it to throw output away. /dev/urandom hands out randomness as if it were an endless file. head -c 16 takes just the first 16 bytes.
/proc is a live X-ray of your running system. /proc/cpuinfo and /proc/meminfo are exactly what tools like top read under the hood — they are mostly just /proc parsers. $$ is the shell's own process ID.
/sys exposes the device and driver model. Reading thermal_zone0/temp gives your Pi's temperature; divide by 1000 to get degrees Celsius.

  • /dev — device nodes. /dev/sda might be a USB disk, /dev/null is the void, /dev/urandom is randomness, /dev/gpiochip0 is your Pi's GPIO pins.
  • /proc — a live, per-process and system-wide view of the kernel's own state. Each running program has a folder /proc/<pid>/ that is a complete X-ray: its open descriptors, memory layout, current directory, and environment.
  • /sys — the structured view of devices, drivers and tunable settings. Some of these you can even write to, to change hardware behaviour like the CPU governor.
Tip: Next time you wonder how a "system tool" works, try to find the file it reads. On your Pi, cat /proc/loadavg shows the same load numbers as uptime, and cat /proc/meminfo is the source free reads from. Once you see this, the whole system stops feeling like a black box.

Named Pipes and Unix Sockets: Files With No Disk Content

An ordinary pipe (a | b) only connects two commands you launched together. But sometimes two unrelated programs need to talk. For that, Linux lets a pipe have a name on the filesystem.

mkfifo /tmp/mypipe
# In terminal A:   cat /tmp/mypipe        (waits here, blocked, until someone writes)
# In terminal B:   echo hello > /tmp/mypipe   (now terminal A prints "hello")

mkfifo creates a named pipe (a FIFO) — a pipe with a filename, so two completely separate programs can connect to it. Notice that the reader blocks, patiently waiting, until a writer shows up. That blocking is the built-in handshake.

A close cousin is the Unix domain socket. It also appears in the filesystem as a special file, but instead of opening it you connect to it. It is faster than networking over localhost because it skips the network stack entirely, and it can pass credentials and even file descriptors between processes. Your Pi uses these everywhere without you noticing: databases, the Docker daemon, and systemd all communicate through Unix sockets.

Try it on your Pi

  1. The redirection-order experiment. Write a tiny script that prints "working..." to stderr and "result" to stdout (use echo working... >&2 for the error line). Run it four ways: plain, > out.txt, > out.txt 2>&1, and 2>&1 > out.txt. Compare what lands on screen versus in the file. Teaches: file-descriptor duplication and why redirection order changes the result.
  2. A log-analysis pipeline. Point cat /var/log/syslog (or any log) into a chain of grep, awk, sort, uniq -c and head to answer real questions: which program logs the most, the busiest hour, the top repeated messages. No scripts — just composed tools. Teaches: the pipe philosophy and the sort | uniq -c | sort -rn counting idiom.
  3. A /proc-only system dashboard. Write a sysinfo script that reads only from /proc and /sys — no free, top or uptime allowed — to print uptime, load average, memory used, and your Pi's CPU temperature. Teaches: that the system "tools" are mostly just /proc parsers, and "everything is a file" in action.
  4. Two programs over a FIFO. Build a tiny job queue: one script echoes commands into /tmp/jobs, another reads from it and runs them. Watch the writer block when no reader is listening. Teaches: named pipes, blocking behaviour, and talking between processes without sockets.

Key terms

  • File descriptor (FD) — a small whole number a program holds while something is open; the kernel maps it to the real file, device, pipe or socket. The unifying handle behind "everything is a file."
  • stdin / stdout / stderr — file descriptors 0, 1 and 2, open by convention in every program: input, normal output, and error output respectively.
  • Redirection — using >, < or 2> to point a file descriptor at a file (or another descriptor) before a program runs. Applied strictly left to right.
  • 2>&1 — "make FD 2 a copy of wherever FD 1 points at this moment." A snapshot, not a live link, which is why redirection order changes the outcome.
  • Pipe — a kernel buffer wiring one program's stdout into another's stdin; the two run concurrently with automatic backpressure. Exists only as descriptors, never as a file on disk.
  • Subshell — a child process the shell forks to run a pipeline stage; its variable changes vanish when it exits, which is why cmd | while read can "forget" a counter.
  • tee — a tool that copies its input to one or more files and passes it through, letting you save and see a stream at once. The idiom for writing to root-owned files via sudo tee.
  • Process substitution — <(cmd) or >(cmd), which hands a program a "filename" that is really a live pipe to another command. Bridges stdin-readers and file-path-takers.
  • /proc — a virtual filesystem the kernel generates on read, exposing live per-process and system-wide state; the real source most "system tools" read from.
  • /sys — a virtual filesystem exposing the device and driver model and tunable settings, some of which you can write to, to control hardware.
  • Named pipe (FIFO) — a pipe given a filename with mkfifo, so unrelated processes can connect; the reader blocks until a writer appears.
  • Unix domain socket — a socket that appears as a special file but is connected to, not opened; faster than localhost networking and able to pass credentials and descriptors between processes.
