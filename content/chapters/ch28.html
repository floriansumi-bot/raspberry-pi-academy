In the last lesson you met a strange truth in passing: you can delete a file you can't write, and you can be locked out of deleting a file you fully own. The reason is the single idea this whole chapter is built on — a filename is not the file. The file is a numbered object called an inode; the name is just a pointer to it, kept in a directory. Once that clicks, a dozen Linux mysteries fall into place at once: why mv is instant, why deleting an open file doesn't free any space, why a backup of ten copies can cost the size of one. We're going deeper now — past the commands, into how storage really works underneath. And it's all real on your Pi, because your Pi boots off a microSD card or SSD running full Debian, and inodes, links, and journaling apply to every byte of it.

The inode: the file behind the name

When you create a file, the kernel quietly does two separate things. First it allocates an inode — a small numbered record holding everything about the file except its name: the owner, the permissions, the timestamps, the size, a count of how many names point at it, and the pointers to the actual data blocks on the disk. Then, second, it adds a directory entry — a single line in the parent directory that says "the name notes.txt means inode number 8472".

So the name and the file are genuinely two different things, living in two different places. You can look at both:

ls -i notes.txt        # show just the inode number behind this name
stat notes.txt         # the whole inode: size, blocks, link count, uid/gid, the three timestamps
df -i                  # inode usage per filesystem -- yes, you can run OUT of inodes
In plain words: A directory is just a phone book — a list mapping names to inode numbers. The inode is the actual person. The name in the book is only a way to look them up. Change the book and you change who answers to a name; you haven't touched the person.

That df -i line hides a real-world gotcha worth knowing on a Pi. Each inode is a fixed slot, and a filesystem is created with a finite number of them. If you fill a card with millions of tiny files — think a runaway cache or a huge mail spool — you can run out of inodes while df still shows gigabytes free, and new files will fail with "No space left on device" even though there clearly is space. When that happens, df -i is the command that tells you the truth.

The key insight: the name is a pointer, and the inode is the real object. Almost everything else in this lesson is just that one fact playing out in different situations.

Hard links vs symlinks

If a name is just a pointer to an inode, then nothing stops two names from pointing at the same inode. That's a hard link: a second directory entry for the exact same file. There's no "original" and no "copy" — both names are equal peers pointing at one inode, and the inode's link count simply goes up by one.

A symbolic link (symlink, or soft link) is a completely different animal. It's a tiny file of its own, with its own inode, whose entire content is a path string — literally the text of where to look. Following it means reading that string and going to that path, wherever it leads.

Hard link Symbolic (soft) link
What it is another directory entry pointing at the same inode a tiny file whose content is a path string
Is there an "original"? no — all names are equal peers yes — it points at a name
Can it cross filesystems? no (inode numbers are per-filesystem) yes
Can it point to a directory? no (generally) yes

How you make one ln a b ln -s target name 
echo hi > a
ln a b               # hard link: 'ls -i' now shows a and b with the SAME inode number
rm a                 # b still works perfectly -- the data is freed only when link count -> 0
ln -s /etc/hosts h   # soft link: h's content is literally the string "/etc/hosts"

That difference in the last two rows is where people get burned, so it's worth saying plainly. A hard link doesn't care what happens to the other names — delete every other entry and the data stays alive as long as one name (one link) remains. A symlink, by contrast, only remembers a path. Move or rename the thing it points at and the symlink doesn't follow; it just keeps pointing at a path where nothing lives any more — a dangling link. ls often shows these in an alarming red.

The key insight: a hard link points at the file (the inode); a symlink points at a name. That's why moving the target breaks one and not the other.

Why mv is instant — and why moving across disks isn't

Here's a satisfying payoff. When you mv a 100 GB file to a new location on the same filesystem, it happens instantly. No progress bar, no waiting. Why? Because a move within one filesystem doesn't touch the data at all — it just rewrites a directory entry. The inode never changes; only the name pointing at it does. Renaming is editing the phone book, not moving the person.

But mv that same file to a different filesystem — say from the microSD card to a USB drive — and suddenly it takes real time. That's because the destination is a separate filesystem with its own, separate set of inode numbers. There's no way to just re-point a name; the data has to be genuinely copied across and then the original deleted. Same command, completely different amount of work, and now you know why.

This is also exactly why hard links can't cross filesystems: a hard link is two names sharing one inode number, and an inode number only means anything within its own filesystem. A symlink can cross freely because it stores a path string, which works anywhere.

The myth of "rm frees space"

This one surprises almost everyone, and it's the source of a classic Pi headache: a disk that's mysteriously full with nothing to show for it.

Myth vs reality: Myth — "When I rm a file, its disk space is freed immediately." Reality — rm performs an unlink: it removes the name and decrements the inode's link count. The inode and its data blocks are freed only when the link count reaches 0 and no process still has the file open. So if a running program is holding the file, deleting its name frees nothing — the program keeps reading and writing it happily, and the disk space stays consumed until that program closes the file or exits.

This is the "phantom disk space" bug in the flesh. A log file grows huge, someone rms it to reclaim space, but the service that writes the log still has it open — so the space never comes back. The tell-tale sign is that df (which asks the filesystem how full it is) reports the disk nearly full, while du (which adds up the files it can actually see by name) reports far less. The gap between them is space held hostage by deleted-but-still-open files.

df -h /                       # filesystem says: nearly full
du -sh / 2>/dev/null          # adding up visible files says: much less -- where's the rest?
sudo lsof +L1                 # the smoking gun: open files whose link count has dropped to 0
sudo lsof | grep deleted     # same idea, shown as '(deleted)' next to the path

The fix is simply to make the process let go: restart the service (or, more surgically, truncate the file through its open file descriptor). And far from being a bug, this behaviour is a feature that log rotation depends on — a logger can keep writing to a file that's already been unlinked and replaced, with no gap and no crash, exactly because the open descriptor keeps the old inode alive until the process is told to reopen.

The FHS: where things live and why

Now that you trust the plumbing, a quick map of the house. The Filesystem Hierarchy Standard gives every top-level directory a defined job, so software written anywhere knows where to put things. On your Pi these are the ones worth committing to memory:

They're virtual filesystems: /proc and /sys are live windows the kernel paints for you, and /run and often /tmp are tmpfs, which lives in RAM and vanishes at reboot. Fast, but never put anything there you want to keep.

Journaling: surviving a power cut

Pis get unplugged. No clean shutdown, just the cord — and yet the card almost always comes back fine. That's journaling doing its job. A journal is a small write-ahead log: before the filesystem makes a change, it writes down its intention to make that change. Then it does the work. If the power dies mid-write, the filesystem on the next boot simply replays the journal to finish or undo the half-done operation — a few seconds — instead of laboriously scanning every inode on the whole card with fsck.

Your Pi's ext4 filesystem journals by default in a mode called data=ordered: it journals the metadata, but guarantees the actual data is safely on the disk before the metadata that points to it is committed. That ordering is the pragmatic sweet spot — it protects you from the worst corruption without the speed cost of journaling every byte twice.

Tip: Journaling protects the filesystem's structure, not necessarily the last few seconds of your data. For a Pi that gets yanked off power a lot, still shut down cleanly when you can — and keep backups (see the last project).

What your Pi uses (ext4) vs what big servers use

Raspberry Pi OS formats your card as ext4, and that's the right default: boring, reliable, and bulletproof. But it's worth knowing what the bigger filesystems add, because the comparison teaches one genuinely beautiful idea — copy-on-write.

Filesystem Character Reach for it when
ext4the reliable default (what your Pi uses); journaling, extents; no snapshots or checksumsyou want boring and bulletproof
XFShigh-throughput, great with huge files and many parallel writers; can grow but not shrinkbig data, many parallel writers
btrfscopy-on-write: snapshots, subvolumes, checksums (catches bit-rot), built-in RAID, compressionsnapshots & integrity on Linux-native storage
ZFSthe integrity gold standard: CoW, end-to-end checksums, snapshots, volume management + RAID-Z; RAM-hungrydata you must not lose — NAS and storage servers

The magic word in the bottom two rows is copy-on-write (CoW). On btrfs and ZFS, taking a snapshot is nearly instant and nearly free, because nothing is actually copied. A snapshot just says "remember all the blocks exactly as they are right now" and shares them. Only when a block later changes does the filesystem write a fresh copy of that one block, leaving the old one in place for the snapshot to keep pointing at. Hence the name: copy on write, not before.

The key insight: a CoW snapshot of a 50 GB volume costs essentially zero space and zero time at first, then grows only by the size of what you change afterwards. That's what makes effortless point-in-time rollbacks possible on the big servers — and, interestingly, the same dedup idea is exactly what we'll use to fake snapshots on your plain ext4 Pi in the last project, using hard links.

LVM: a flexible layer beneath the filesystem

One more layer to name, because you'll meet it on bigger Linux boxes even if your Pi doesn't use it by default. LVM (the Logical Volume Manager) sits between raw disks and the filesystem, turning rigid partitions into a flexible, resizable pool:

physical disks  ->  PV (physical volume)  ->  VG (volume group = a pool)  ->  LV (logical volume)  ->  filesystem

With LVM you can grow a "partition" across several disks, snapshot it, or migrate it to new hardware — all without repartitioning. It's a software-defined, stretchy abstraction over the physical disks. (btrfs and ZFS fold this same capability into the filesystem; with ext4 or XFS you add LVM underneath to get it.) To see the whole stack of disks, partitions, and mounts on any Linux box:

lsblk                  # the block-device tree: disks -> partitions -> mountpoints
findmnt                # what's mounted where, as a readable tree
mount | column -t      # the same information, one mount per line

Try it on your Pi

  1. Watch an inode and a link count with your own eyes. Run echo hi > a, then ls -li a and note the inode number and the link count (the small number after the permissions). Now hard-link it twice with ln a b and ln a c, and add a symlink with ln -s a s. Run ls -li a b c s: a, b, and c all share one inode number and the link count now reads 3, while s has its own inode and an arrow pointing at a. Finally delete the "original" with rm a: confirm b and c still print "hi" perfectly (the data lives on, link count now 2) but s is now dangling and broken. Explain every number out loud — that's the lesson.
  2. Prove that deleting an open file frees nothing. In one terminal, start a process that holds a file open and keeps writing: yes > /tmp/big.log & (let it grow for a few seconds, then note the size). In a second terminal, watch df -h /tmp shrink. Now rm /tmp/big.log — and watch df not recover the space, while du -sh /tmp can't even see the file any more. Run sudo lsof +L1 or sudo lsof | grep deleted to find the still-open deleted file. Then kill the yes process and watch df finally jump back. You just reproduced the phantom-disk bug — and the mechanism log rotation relies on.
  3. Build a Time-Machine-style backup with rsync --link-dest. Plug in a USB drive. Make a snapshots folder on it, then back up your home directory so that unchanged files are hard-linked to the previous snapshot instead of copied: rsync -a --link-dest=/mnt/usb/backups/latest /home/pi/ /mnt/usb/backups/$(date +%F-%H%M)/, then repoint a latest symlink at the new snapshot. Run it twice with a small change in between, and check the disk usage: ten snapshots of a 1 GB home folder cost roughly 1 GB plus only what changed, because every unchanged file is one inode shared across all snapshots. You've just rebuilt copy-on-write snapshots out of plain ext4 and hard links.

Key terms

  • inode - The real file object: a numbered record holding metadata (owner, permissions, timestamps, size, link count) and pointers to the data blocks — everything except the name.
  • directory entry - A single line in a directory mapping a name to an inode number; this is where a filename actually lives.
  • hard link - A second directory entry pointing at the same inode; an equal peer, not a copy. The data survives until the inode's link count drops to 0.
  • symlink (soft link) - A tiny file whose content is a path string; it points at a name, so it breaks (dangles) if the target is moved or deleted.
  • link count - The number of hard links (names) pointing at an inode; the data is freed only when this reaches 0 and no process holds the file open.
  • unlink - What rm really does: remove a name and decrement the link count, rather than directly erase data.
  • FHS (Filesystem Hierarchy Standard) - The standard giving each top-level directory (/etc, /var, /usr…) a defined job.
  • journaling - A write-ahead log of intended changes that lets a filesystem replay (not full-scan) after a crash; ext4 on the Pi uses data=ordered.
  • copy-on-write (CoW) - The btrfs/ZFS technique where a snapshot shares blocks and a fresh copy of a block is written only when it changes — making snapshots near-instant and near-free.
  • tmpfs - A RAM-backed filesystem (/run, often /tmp) that is fast and volatile — gone at reboot.
  • LVM (Logical Volume Manager) - A resizable abstraction (PV → VG → LV) between raw disks and the filesystem, allowing growth, migration, and snapshots without repartitioning.
